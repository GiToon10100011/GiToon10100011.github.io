### 1\. DOM 설명

DOM이란 HTML이나 XML 같은 마크업 언어로 작성된 문서를 자바스크립트와 같은 프로그래밍 언어가 조작할 수 있도록 하는 인터페이스를 의미합니다. DOM은 계층적 구조를 가진 노드 트리로 구성됩니다. **_DOM은 왜 필요한가요?_**

동적인 웹 페이지를 구현하려면 자바스크립트와 같은 프로그래밍 언어가 문서에 접근하고, 제어할 수 있는 수단이 있어야 합니다. 하지만, 마크업 언어로 작성된 문서에는 이러한 수단이 없습니다. TV는 있지만, TV를 조작할 수 있는 리모콘이 없는 것과 같은 이치라고 볼 수 있는거죠. 따라서, 문서에 접근하고, 제어할 수 있는 수단인 DOM이 필요합니다. **_DOM을 통해 어떤 동작을 할 수 있는지 예를 들어주세요_**

button element가 클릭되었을 때, 특정 함수를 호출하도록 Event Handler를 추가할 수 있고, 웹 페이지 내에 새로운 요소를 추가하거나, 삭제, 수정할 수 있습니다. **_DOM은 왜 계층적 구조로 표현하는지 설명해주세요_**

계층적 구조에서는 노드들 간의 관계가 부모, 자식, 형제 등으로 명확하게 정의됩니다. 이는 노드의 추가, 제거, 이동 작업을 쉽게 할 수 있도록 도와줍니다. 또한, 이벤트가 발생한 요소로부터 이벤트가 올라가는 이벤트 버블링, 반대로 이벤트가 내려가는 이벤트 캡처링 동작은 계층적 구조에서 효율적으로 동작하기 때문에, DOM을 계층적 구조로 표현하는 것입니다.

<br>

**_이벤트버블링/캡처링_**

이벤트 버블링(event bubbling)은 HTML에서 이벤트가 발생했을 때, 해당 요소에서 이벤트가 처리된 후, 상위 요소로 이벤트가 전파되는 현상을 말합니다. 이벤트 버블링은 이벤트가 전파되는 동안 부모 요소에서도 이벤트를 감지할 수 있다는 장점이 있습니다. 즉, 이벤트를 처리하는 핸들러 함수를 부모 요소에 등록해놓으면, 자식 요소에서 발생한 이벤트도 모두 처리할 수 있습니다. 이를 활용하면, 여러 개의 하위 요소에서 발생하는 이벤트를 하나의 이벤트 핸들러로 바인딩하는 이벤트 위임 처리를 할 수 있습니다.

<br>

이벤트 캡처링은 버블링과 반대로 최상위 요소에서 시작해 이벤트가 발생한 요소까지 내려가는 전파 방식입니다. 캡처링은 addEventListener의 세 번째 인자를 true로 설정하여 활성화할 수 있습니다.

<br>

버블링 및 캡쳐링을 방지하기 위해서는 이벤트 객체 stopPropagation() 메서드를 사용하여 이벤트 전파를 중지시키거나, 이벤트 핸들러에서 이벤트가 발생한 요소를 확인하여 처리해야 합니다.

<br>

### 2\. VDOM이란?

웹성능을 최적화하기 위해 사용되는 dom관리 방법입니다.

웹 어플리케이션의 상태 변경시, 객체 형태의 가상 돔을 통해 변경된 부분만 찾아내어 이를 실제 돔에 적용하는 기능을 합니다.

가상돔의 동작 순서는 가상돔에서 변경점을 찾아내는 과정 diffing, 찾아낸 변경점을 실제 돔에 적용하는 과정인 reconcilation 크게 두가지로 구분할 수 있습니다.

<br>

**_동작하는 간단한 예시_**

<br>

어플리케이션이 제일 처음 렌더링 될때, 어플리케이션의 초기 상태를 담은 가상돔을 메모리상에 하나 생성하여, 어플리케이션이 실행되면서 상태나 프롭스가 변경된 부분이 있으면 새로운 가상돔을 메모리상에 하나 더 생성합니다. 새로운 버전의 가상돔과 이번 버전의 가상돔과 비교하는 과정인 diffing에 돌입하여 변경점을 찾아내며, 이 과정에서 두 가상돔 트리의 각 노드를 비교하여 어떤 부분이 변경됐는지 확인하고 실제 돔에 적용하는 과정인 리컨실레이션에 돌입하게 됩니다. 변경된 부분만 실제 돔에 업데이트하기에 브라우저 성능이 향상될 수 있습니다. 리컨실레이션이 완료된 후, 또 다른 변경점이 생기면 구 버전의 가상돔이 폐기되고, 새로운 변경 사항을 반영한 최신 버전의 가상돔이 다시 생성됩니다.

<br>

**_state나 props가 변경될 때마다 디핑과 리컨실레이션이 실행되는가?_**

<br>

리엑트를 비롯하여 가상돔을 사용하는 대부분의 프레임워크에서는 여러개의 상태 변화를 하나로 묶어서 배치 업데이트를 지원하고 있습니다. 따라서 짧은 시간내 여러개의 상태변화가 일어나도 한꺼번에 모아서 처리되어 diffing과 reconcilation은 한번만 일어납니다. 

<br>

**_가상돔을 사용하는 것이 그렇지 않은것보다 좋은지?_**

<br>

항상 그런것은 아닙니다. 가상돔도 메모리 공간을 차지하며, diffing하는 과정 역시 cpu를 활용하기에 간단한 어플리케이션이라면 오히려 오버헤드를 초래할 수 있습니다. 

그러나 dom 트리가 복잡하고 상태변경이 많이 일어나는 대규모 어플리케이션이라면 사람의 인지 능력으로 정확히 어떤 dom요소를 업데이트해야하는지 식별하기 어렵기 때문에 가상돔을 사용하는 것입니다.

### 3\. Promise의 개념

Promise는 비동기 연산의 상태를 나타내는 객체입니다. 비동기 처리가 진행중이면 pending, 성공이면 fulfilled, 실패면 rejected라는 상태값을 가집니다. Promise는 비동기 프로그래밍을 then과 catch의 체이닝을 통해 보다 간결하게 표현할 수 있도록, ES6에서 새로 도입되었습니다. **_Promise 등장 이전에는 어떤 방식으로 비동기 처리를 했는지 설명해주세요_**

Promise 등장 이전에는 비동기 작업을 처리하는 함수에 성공 콜백과, 실패 콜백을 각각 넘겨서 완료 상태에 따른 처리를 했습니다. 이런 방식이다 보니, 두 개 이상의 비동기 작업이 순서를 갖고 실행되어야 할 때, 콜백 함수 안에 또다른 콜백 함수가 점점 중첩되는 callback hell 현상이 발생하여, 코드 가독성 및 유지보수성 저하의 요인이 되곤 했습니다. **_async-await에 대해 설명해주세요_**

Promise의 완료를 기다리기 위한 문법으로, async 키워드로 정의한 함수 내에서 호출되는 Promise 앞에 await 키워드를 쓰면, 해당 Promise가 완료될 때까지 코드의 실행을 일시정지할 수 있습니다. 이를 통해, 비동기 코드를 마치 동기 코드처럼 쉽게 작성할 수 있습니다. **_async-await 를 사용할 때 주의해야할 점을 알려주세요_**

await의 에러 핸들링은 catch메소드를 통해 에러를 처리하는 Promise와는 달리, try-catch 블록에서 해야합니다. 이는 try-catch블록없이 await에서 에러가 발생시, 해당 에러는 함수밖으로 전파되어 Promise가 reject상태가 되어 어플리케이션이 예기치 않게 종료될 수 있기 때문입니다.

또한, await는 Promise가 완료될 때까지 함수의 실행을 중단하기 때문에, 실행 흐름을 잘 고려하여 적재적소에 써야합니다. 예를 들어, 여러 비동기 작업이 순차적으로 진행될 필요가 없는 경우는, await 대신 Promise.all 함수를 사용하는 것이 바람직합니다.

### 4\. React의 키란? 

Key는 리스트를 매핑하여 동일한 컴포넌트를 여러 개 렌더링할 때 각 컴포넌트에 전달되는 고유한 값입니다. 재조정 단계에서 각 노드의 key 값들을 비교하여 리스트에 추가, 삭제, 혹은 순서가 변경된 노드를 식별하고, 이를 통해 필요한 re-rendering만 수행하기 위해 사용합니다. **_배열의 index를 key값으로 하면 안되는 이유가 무엇인가요?_**

배열의 인덱스를 key 값으로 사용하면 안 되는 이유는 순서가 변경되어도 동일한 key 값이 유지되기 때문입니다. A,B,C 순서로 rendering되어 있던 컴포넌트가 C,B,A 순서로 변경되어도 key값은 동일하기 때문에, 재조정 단계에서 re-rendering 대상으로 식별하지 않을 가능성이 생깁니다. 따라서, 배열 내에서 순서가 변경되어도 각 컴포넌트의 key값이 변경되지 않는 고유한 값으로 설정해야 합니다. **_고유한 속성값을 주기 어려울 때는 어떤 값으로 대체할 수 있나요?_**

컴포넌트에 전달되는 각 props를 적절히 조합하여 서로 겹치지 않는 id를 만드는 것이 효과적입니다. 이런 방식으로도 고유한 id를 할당하기 어려운 경우에는, 8-4-4-4-12형식을 가지는 랜덤한 UUID를 생성하여 key값으로 전달할 수 있습니다. UUID는 128비트로 이루어져 있기 때문에, 서로 겹칠 가능성이 극히 적기 때문입니다. 하지만, UUID는 비교적 큰 사이즈를 갖기 때문에, 메모리 공간을 효율적으로 사용할 수 없다는 단점이 있습니다.

### 5\. 자료구조에 대한 질문(배열과 연결리스트의 차이점)

배열과 연결리스트는 데이터 저장 방식에서 근본적인 차이가 있습니다.

배열은 메모리에 연속적으로 데이터를 저장합니다. 인덱스를 통해 데이터에 즉시 접근할 수 있어 검색이 빠르지만, 크기가 고정되어 있고 중간에 데이터를 삽입하거나 삭제할 때 효율이 떨어집니다.

연결리스트는 각 노드가 데이터와 다음 노드를 가리키는 포인터로 구성됩니다. 메모리에 연속적으로 위치할 필요가 없어 삽입과 삭제가 효율적이지만, 특정 데이터에 접근하려면 메모리상에 노드가 흩뿌려져있어 처음부터 순차적으로 탐색해야 해서 검색 속도가 느립니다. 

따라서 데이터 접근이 빈번한 경우 배열을, 데이터 삽입/삭제가 빈번한 경우 연결리스트를 선택하는 것이 일반적입니다.

### 6\. CI/CD가 무엇이고 어떻게 구성했으며 어떻게 만들었는가?

CI/CD는 지속적 통합(Continuous Integration)과 지속적 배포(ContinuousDeployment)를 의미합니다. 이는 개발 과정에서 코드 변경사항을 자동으로 빌드, 테스트하고 배포하는 자동화된 프로세스입니다.

제 프로젝트에서는 Vercel과 Netlify 같은 플랫폼을 활용하여 CI/CD를 경험했습니다. 이 플랫폼들은 GitHub 저장소와 연동되어 코드를 푸시하면 자동으로 빌드 및 배포 과정이 실행됩니다.

향후에는 GitHub Actions나 Jenkins 같은 도구를 활용하여 CI/CD 파이프라인을 직접 구축해보고 싶습니다. 자동화된 테스트와 배포 과정을 통해 개발 효율성을 높이고, 안정적인 서비스 제공에 기여하고 싶습니다.

<br>

### 7\. AWS EC2와 AWS Amplify, AWS S3는 무엇인가?

EC2(Elastic Compute Cloud)는 AWS에서 제공하는 가상 서버 서비스입니다. 클라우드에서 컴퓨팅 파워를 제공하여 개발자가 웹 서비스를 호스팅하고 애플리케이션을 실행할 수 있게 해줍니다.  백엔드 서버, API 서버, 데이터베이스 서버 등 다양한 용도로 활용할 수 있습니다.

<br>

AWS S3 (Simple Storage Service) 와 AWS Amplify는 직접 사용해보진 않았으나, 제가 아는 선에서 말씀드리자면 S3는 인터넷 스토리지 서비스로, 파일을 저장하고 인터넷을 통해 접근할 수 있게 해줍니다. 이미지, 비디오, 문서 등 어떤 형태의 파일이든 저장할 수 있으며, 정적 웹사이트 호스팅에 활용되는 걸로 알고 있습니다.

<br>

Amplify는 웹 및 모바일 애플리케이션을 빠르게 구축하고 배포할 수 있는 개발 플랫폼입니다. 프론트엔드 프레임워크(React, Angular, Vue 등)와 통합되어 인증, 스토리지, API 등의 백엔드 서비스를 쉽게 구현할 수 있게 해줍니다. 또한 CI/CD 파이프라인을 자동으로 구성하여 코드 변경 시 자동으로 빌드하고 배포하는 기능을 제공합니다. 특히 프론트엔드 개발자가 백엔드 기능을 쉽게 통합할 수 있도록 설계되어 있어, 풀스택 애플리케이션 개발 시간을 단축시켜 준다하여 향후 프로젝트에 활용해보고 싶습니다. 

<br>

### 8\. 배포직전에 화면이 느리게 뜬다는 피드백을 들었을때 어떻게 할것인지?

### / 프론트가 느리다고 하면 어떻게 할 것인지?

배포 직전에 화면이 느리게 뜬다는 피드백을 받았다면, 먼저 webp 포맷으로 이미지 최적화 및 리사이징을 수행한 후, 불필요한 리렌더링 방지를 위한 React.memo와 useMemo 활용하며 CSS 애니메이션 대신 transform과 opacity 속성 사용 등을 순차적으로 적용할 것입니다. OTT 프로젝트에서도 영화 포스터 이미지 최적화와 Next.js의 Image 컴포넌트 활용으로 초기 로딩 속도를 50% 개선한 경험이 있어, 이러한 접근 방식이 효과적이라고 확신합니다.

<br>

### 9\. 멀티/싱글스레드 & 이벤트루프

멀티스레드는 하나의 프로세스 내에서 여러 개의 스레드가 동시에 작업을 수행하는 프로그래밍 기법입니다. 프로세스가 하나의 작업만 처리하는 싱글스레드 방식과 달리, 멀티스레드에서는 여러 작업을 병렬로 처리할 수 있어 효율성이 높아집니다. 반면 단점으로는 스레드 간 데이터 공유로 인한 동기화 문제(race condition), 교착 상태(deadlock) 등의 복잡한 문제가 발생할 수 있습니다. 이러한 멀티스레드를 지원하는 언어들은 자바, C++, 파이썬, 러스트 등이 있습니다.

<br>

_**동기화문제/교착상태**_

동기화문제는 여러 스레드가 공유 데이터에 동시에 접근하여 수정할 때 발생합니다. 예를 들어, 두 스레드가 동시에 카운터 변수를 증가시키려 할 때, 한 스레드의 작업이 다른 스레드에 의해 덮어쓰여질 수 있습니다.

교착상태는 두 개 이상의 스레드가 서로가 보유한 자원을 기다리며 무한정 대기하는 상황입니다. 예를 들어, 스레드 A가 자원 X를 점유하고 자원 Y를 기다리는 동시에, 스레드 B가 자원 Y를 점유하고 자원 X를 기다리면 교착 상태가 발생합니다.

<br>

_**싱글스레드**_

싱글스레드에서는 하나의 연산이 실행중이면, 스레드가 block되어 두개 이상의 연산이나 함수를 동시에 실행할 수 없습니다. 네트워크 요청, db쿼리, 파일시스템제어 등 시간이 오래걸리는 작업이 메인 쓰레드를 block한다면 심각한 자원낭비와 사용성 저하로 이어집니다. 다행히 자바스크립트 엔진은 긴 시간이 소요되는 작업들을 메인 쓰레드에서 처리하진 않으며 노드js의 경우에는 libuv라는 c++ 라이브러리, 브라우저의 경우 fetch와 같은 웹 api를 통해 백그라운드에서 비동기처리합니다.

<br>

_**콜백함수**_ 

<br>

자바스크립트만으로 프로그램의 기본적인 흐름을 잡을 순 있지만 싱글스레드, 파일시스템 접근, OS수준의 같은 작업엔 한계가 존재합니다.

이 한계를 보완하기 위해 자바스크립트 실행환경내에 자바스크립트로 접근 가능한 비동기처리를 비롯한 여러기능들을 백그라운드에서 처리하도록 만들었습니다. 백그라운드 실행 여부를 메인쓰레드가 알아야하고, 처리완료 시 메인쓰레드에서 실행할 함수를 전달해야하는데 이를 콜백함수라고 한다. 콜백 함수는 비동기 작업이 완료된 후 호출되어 결과를 처리하거나 다음 작업을 진행하는 역할을 합니다.

<br>

**_이벤트루프_**

<br>

콜백함수는 백그라운드에 잠깐 전출되어 언젠간 다시 메인쓰레드안으로 돌아와야하는데, 메인쓰레드와 백그라운드는 별도의 프로세스이므로,  메인쓰레드에 이미 진행중인 연산이 있을 수 있어 콜백함수가 돌아올 타이밍이 애매해질 수 있습니다. 이를 위해 콜백이 돌아올 시점을 정해주는 체계가 필요하며, 이 역할을 담당하는 것이 이벤트 루프입니다.

<br>

메인쓰레드에서 실행되는 모든 함수들은 호출 시,  콜스택이라는 공간에 LIFO형태로 차곡차곡 쌓이게 됩니다. 

이때, 만약 콜스택에 비동기 함수가 들어오면 즉시 팝하여 백그라운드로 전달됩니다. 비동기가 백그라운드에서 처리되는 한편, 콜스택에서 다음 함수가 계속해서 실행되며, 이후 백그라운드에서 비동기가끝나면 콜백 함수가 이벤트 큐라는 공간에 FIFO구조로 쌓이게 됩니다. 여기서 이벤트 루프가 등장하는데, 이벤트 루프는 이벤트 큐에서 콜스택으로 콜백 함수를 이동시켜주는 역할을 합니다. 이벤트 루프는 콜스택이 비어있는지 수시로 확인하며, 비어있다면 이벤트 큐에서 콜백을 콜스택에 푸시해줍니다. 이벤트큐와 콜스택 사이에 있는 일종의 신호등인 셈인거죠.

<br>

**_이벤트루프 간단정리_**

1. 모든 함수 호출은 콜스택에 lifo 구조로 쌓인다.
2. 비동기 함수는 콜 스택에 들어오는 즉시 pop되어 백그라운드로 보내진다.
3. 백그라운드에서 처리가 완료되면, 콜백함수는 이벤트 큐에 fifo 구조로 쌓인다. 
4. 이벤트 루프는 콜스택이 비어있는지 수시로 확인한다.
5. 콜스택이 비어있을 경우, 이벤트 루프는 이벤트 큐에서 콜백함수를 이동시킨다. 
6. shift된 콜백함수는 콜스택으로 옮겨져 실행된다. 

<br>

### 10\. reflow&repaint

reflow란 웹페이지 내에서 요소의 위치 또는 크기에 변화가 있을때 변화된 레이아웃을 다시 계산하여 렌더 트리에 적용하는 과정입니다.

width나 height같은 크기 속성이나, position과 같은 위치속성, display같은 레이아웃관련 속성, font-size같은 폰트관련 속성들이 전부 리플로우를 유발하는 속성입니다.

<br>

**_repaint란?_**

웹페이지 내에서 요소의 시각적인 표현에 변화가 있을때 변화된 시각적 표현을 다시 계산하여 렌더트리에 적용하는 과정입니다.

color, background-color, border-color 등과 같은 속성들이 리페인트를 유발합니다.

<br>

**_reflow와 repaint의 성능상 차이점_**

부모노드의 레이아웃변화는 자식노드의 레이아웃까지 영향을 미쳐, 리페인트와 달라 리플로우가 발생하면 하위 렌더트리를 재계산 재구성하는 과정이 필요하여 그 자체만으로 부하가 큰 작업입니다. 또한, 리플로우가 발생한다면 일반적으로 리페인트도 다시 발생하여 성능에 큰 영향을 미쳐 렌더링 성능을 최적화하기 위해 리플로우를 최소화해야합니다. 참고로 리플로우는 cpu, 리페인트는 gpu를 활용합니다.

<br>

**_reflow를 최소화하기 위한 방법_**

먼저 dom 업데이트를 한번에 묶어 배치 처리를 해야하며, offsetHeight, offsetWidth같은 계산된 스타일 속성에 여러번 즉시 reflow가 유발되어 이러한 속성들은 변수에 저장해두고 재사용할 필요가 있습니다.

또한, CSS 애니메이션에는 transform과 opacity 같은 GPU 가속 속성을 사용하여 reflow 대신 repaint만 발생시키도록 하는것이 좋습니다.

마지막으로 레이아웃 변경이 적은 position의 fixed나, absolute같은 속성을 사용하여 해당 요소의 변경이 다른 요소에 미치는 영향을 최소화하는 것이 좋습니다.

<br>

### 11\. 브라우저 렌더링 부하를 줄이기 위해 생각하는 알고리즘

먼저, 페이지 초기 로드 시 필요한 컴포넌트만 로드하고, 나머지는 필요할 때 동적으로 로드하는 방식인 Lazy Loading기법이 있습니다. React.lazy()와 Suspense를 활용하여 이러한 코드 스플리팅을 구현할 수 있습니다. 코드 스플리팅을 통해 초기에 필요한 코드만 다운로드하고 나머지는 사용자가 특정 기능이나 페이지에 접근할 때 로드하도록하여 초기 로딩 시간을 단축시켜 사용자가 웹사이트와 더 빠르게 상호작용할 수 있습니다.

<br>

또한 스크롤, 리사이즈, 입력 이벤트 같이 빈번하게 발생하는 이벤트의 처리 횟수를 제한하는 기법인 디바운싱/스로틀링을 사용할 수 있습니다. 디바운싱은 연속된 이벤트 중 마지막(또는 첫번째) 이벤트만 처리하고, 스로틀링은 일정 시간 간격으로 이벤트를 처리합니다. 

디바운싱의 경우 예를들어 검색창에 타이핑할 때, 사용자가 타이핑을 멈춘 후 500ms가 지났을 때만 검색 API를 호출합니다. 이렇게 하면 사용자가 "react"라고 입력할 때 'r', 're', 'rea', 'reac', 'react' 각각에 대해 API를 호출하지 않고, 최종 "react"에 대해서만 한 번 호출합니다.

쓰로틀링의 경우, 스크롤 이벤트에서 무한 스크롤을 구현할 때, 스크롤 이벤트가 발생할 때마다가 아니라 200ms마다 한 번씩만 스크롤 위치를 체크하고 필요시 새 데이터를 로드합니다. 이렇게 하면 빠르게 스크롤해도 과도한 API 호출을 방지할 수 있습니다.

<br>

계산 비용이 큰 함수의 결과를 캐싱하여 동일한 입력에 대해 재계산을 방지하는 기법인 메모이제이션 또한 활용할 수 있습니다. React에서는 useMemo, useCallback, React.memo를 활용하여 불필요한 재렌더링을 방지할 수 있습니다.

<br>

**마지막으로** transform, opacity 같은 GPU 가속 속성을 활용하고, 레이아웃을 변경하는 속성(width, height, top, left 등)의 애니메이션은 피하여 CSS애니메이션 최적화를 할 수 있습니다. requestAnimationFrame을 사용하여 애니메이션 프레임을 브라우저의 렌더링 주기에 맞춥니다.

<br>

### 12\. 지역/전역변수는 무엇이 다른지?

전역 변수는 프로그램 전체에서 접근할 수 있는 변수로, 자바스크립트에서는 함수 외부에서 선언되거나 window 객체에 속한 변수를 말합니다. 이러한 전역 변수는 어디서든 접근 가능하고 프로그램이 종료될 때까지 메모리에 유지되는 특징이 있습니다.

<br>

반면 지역 변수는 특정 범위 내에서만 접근할 수 있는 변수입니다. 함수 내부에서 선언된 변수나 블록 스코프 내에서 선언된 변수가 여기에 해당합니다. 지역 변수는 선언된 범위 내에서만 접근 가능하고, 해당 범위의 실행이 끝나면 가비지콜렉터를 통해 메모리에서 해제됩니다.

실제 개발에서는 전역 변수 사용을 최소화하고 필요한 경우에만 지역 변수를 활용하는 것이 좋습니다.

<br>

### 13\. 이미지 사이즈 최적화 방법 / 최적화된 용량은 어느정도?

이미지 최적화를 위해 WebP 같은 최신 포맷을 사용하고, 이미지 압축 도구로 품질을 유지하면서 용량을 줄이는 것이 효과적입니다. Next.js의 Image 컴포넌트나 img 태그의 srcset 속성을 활용해 디바이스에 맞는 크기의 이미지를 제공하고, lazy loading을 적용하면 초기 로딩 속도를 개선할 수 있습니다.

<br>

웹 페이지의 이미지 적정 용량은 용도에 따라 다르지만, 일반적으로 히어로 이미지(큰 배너이미지)는 200-300KB, 썸네일은 20-30KB 이하가 권장됩니다. 전체 페이지의 이미지 총량은 1MB 이내로 유지하는 것이 좋은 사용자 경험을 위해 중요합니다.

<br>

### 14\. React Suspense란? 

React Suspense는 데이터 로딩이나 코드 분할 같은 비동기 작업을 처리하는 동안 대체 UI를 표시할 수 있게 해주는 React의 기능입니다. 내부 컴포넌트가 준비될 때까지 fallback UI를 보여줍니다. OTT 프로젝트에서 영화 데이터 로딩 중에 스켈레톤 UI를 표시하는 데 활용했으며, 이를 통해 사용자 경험을 크게 개선할 수 있었습니다.

### 15\. 브라우저 렌더링 원리

먼저 서버로부터 HTML 문서를 전달받으면, 브라우저 엔진은 위에서 아래로 순차적으로 파싱하며 태그와 속성을 발견합니다. 이 태그와 속성들은 트리 형태로 변환되어 메모리에 저장되는데, 이를 DOM 트리라고 합니다. HTML 파싱 중 CSS 링크 또는 스타일 태그를 만나면, 이를 파싱하여 CSSOM 트리로 변환합니다. 문서의 파싱이 완료되면, DOM과 CSSOM 트리를 결합하여 렌더 트리를 생성합니다. 렌더 트리는 브라우저 상에서 요소의 위치와 크기를 결정하는 리플로우 과정을 거치며, 마지막으로 요소의 색상과 같은 시각적 요소를 그리는 페인팅 과정이 진행됩니다. **_HTML 파싱 중간에 script 태그를 만나면 어떻게 되나요?_** 파싱 중간에 \`script\` 태그를 만나면, 브라우저는 해당 스크립트를 로드하고 실행하기 위해 파싱을 일시 중단합니다. 외부 스크립트의 경우, 스크립트를 로드하고 실행한 후 파싱을 재개하며, 내부 스크립트의 경우, 실행이 완료될 때까지 파싱이 중단됩니다. 이로 인해 파싱 속도가 저하되고, DOM 트리가 완성되기 전에 스크립트가 DOM을 조작할 가능성이 있어, 예기치 못한 상황이 발생할 수 있습니다. 이러한 문제를 방지하기 위해 async나 defer속성을 사용하여 파싱에 미치는 영향을 최소화할 수 있습니다. **_async와 defer 속성에 대해 설명해주세요_** \`async\`와 \`defer\`는 스크립트를 비동기적으로 로드하는 속성입니다. 이들은 HTML 파싱이 중단되는 현상과 DOM 트리가 완성되기 전에 스크립트가 실행되는 것을 방지하기 위해 사용됩니다. \`async\` 속성은 스크립트가 로드되는 즉시 실행하는 반면, \`defer\` 속성은 스크립트를 비동기적으로 로드하되, HTML 파싱이 완료된 후 스크립트를 실행합니다. 따라서 \`async\`는 스크립트 로드 순서 상관없이 실행되는 경우에 적합하고, \`defer\`는 스크립트의 실행 순서가 중요할 때 적합합니다.  

  

### **16\. 비동기 함수에 대해**

비동기 함수(Asynchronous function)는 함수의 실행 결과가 즉시 반환되지 않고, 특정 조건이 충족될 때까지 기다리는 함수입니다. 비동기 함수는 일반적으로 콜백 함수나 Promise 객체를 반환합니다. 콜백 함수는 비동기 작업이 완료되었을 때 호출되는 함수이며, Promise 객체는 비동기 작업이 성공적으로 완료되었는지 또는 실패했는지를 나타내는 객체입니다. 

그러나 비동기 함수를 사용할 때는 콜백 지옥과 같은 문제를 피하기 위해 적절한 에러 처리와 코드 구성이 필요합니다. 여러개의 비동기 함수가 실행되면, 이벤트 루프는 비동기 함수 호출을 처리하고, 비동기 함수가 완료되었을 때 콜백 함수를 호출합니다. 따라서, 여러 개의 비동기 함수가 실행될 때 이들 함수는 동시에 실행되며, 이벤트 루프에 의해 비동기 함수의 실행 순서가 제어됩니다.

  

### 17\. TTD

TTD(Test-Driven Development)는 웹 렌더링 방식과는 별개로, 테스트 코드를 먼저 작성한 후 실제 코드를 개발하는 소프트웨어 개발 방법론입니다. 요구사항을 테스트 케이스로 변환한 뒤, 테스트를 통과하는 코드를 작성하는 방식으로 진행됩니다.

### 18\. AJAX

Ajax는 자바스크립트를 통해 서버와 브라우저가 비동기 방식으로 데이터를 교환할 수 있는 통신기능입니다. 페이지 전체를 새로고침하지 않고도 서버에서 데이터를 요청하고 받아와 화면의 일부만 업데이트할 수 있게 해줍니다. 현대 웹에서는 XML 대신 JSON 형식을 주로 사용하며, fetch API나 axios 같은 라이브러리로 구현합니다.

<br>

### 19\. API

API(Application Programming Interface)는 서로 다른 소프트웨어 시스템이 상호작용할 수 있게 하는 규칙과 도구의 집합입니다. 개발자가 특정 기능이나 데이터에 접근할 수 있도록 정의된 방법을 제공하며, 복잡한 코드를 추상화하여 간단한 인터페이스로 사용할 수 있게 합니다. 웹 개발에서는 주로 REST API나 GraphQL API를 통해 클라이언트와 서버 간 데이터를 주고받습니다.

<br>

### 20\. REST/Restful API

REST(Representational State Transfer)는 웹 서비스를 설계하는 아키텍처 스타일입니다. RESTful API는 이 원칙을 따르는 API로, GET, POST, PUT, DELETE등과 같은 HTTP 메서드를 사용해 리소스를 조작합니다. 주요 특징으로는 클라이언트-서버 구조, 무상태성(Stateless), 캐시 가능성, 계층화된 시스템, 그리고 URI를 통한 리소스 식별이 있습니다. RESTful API는 직관적인 엔드포인트와 표준 HTTP 상태 코드를 사용하여 웹 서비스 간 효율적인 통신을 가능하게 합니다.

<br>

### 21\. HTTP메소드

GET은 서버에서 리소스(데이터)를 요청하는 메소드입니다. 요청한 데이터를 가져와 응답합니다.  
POST는 서버에 데이터를 전송하는 메소드입니다. 데이터를 전송하여 서버에서 처리하고, 처리 결과를 응답합니다. POST방식은 URL에 데이터가 노출되지 않아 GET보다 보안성이 높습니다. 멱등성이 없어, 같은 요청을 여러 번 보내면 여러 번 처리되며, 브라우저에서 새로고침 시 데이터가 재전송될 수 있어 주의가 필요합니다.  
PUT은 서버에 데이터를 업데이트하는 메소드입니다.   
DELETE는 서버에서 데이터를 삭제하는 메소드입니다. 

<br>

### 22\. 주소창에 google.com을 입력하면 일어나는 일

사용자가 웹 브라우저를 통해 주소를 입력하면, URL 주소 중 도메인 네임을 DNS 서버에서 검색합니다.

DNS 서버에서 해당 도메인에 해당하는 IP주소를 찾아, 사용자가 입력한 URL 정보와 함께 전달합니다.

브라우저는 HTTP 프로토콜을 사용해 요청 메세지를 생성하고, HTTP 요청 메세지는 TCP/IP 프로토콜을 사용해 서버로 전송하게 됩니다.

서버는 response 메세지를 생성해 다시 브라우저에게 데이터를 전송합니다.

브라우저는 response를 받아 파싱 후 화면에 최종적으로 렌더링하게 됩니다.

<br>

**_DNS란 뭔가요?_**

DNS는 도메인 네임 시스템의 약자로, 사람이 읽을 수 있는 도메인 명을 머신이 읽을 수 있는 IP 주소로 변환하는 과정에서 개입하는 것이 `DNS` 서비스 입니다. 포트폴리오 프로젝트에서 aws의 dns 서비스인 route 53을 통해 커스텀 도메인을 등록했습니다.

<br>

**_URL이란 뭔가요?_**

Uniform Resource Locator의 약자로, 인터넷 리소스를 가리키는 표준명칭입니다. 서버의 자원을 요청할 때 사용되며 URL을 통해 인터넷 상의 모든 리소스를 요청할 수 있으며 HTTP/FTP등의 자원요청도 가능해집니다.

<br>

### 23\. HTTP 프로토콜/상태코드

HTTP(Hypertext Transfer Protocol)는 웹에서 클라이언트와 서버 간에 데이터를 주고받기 위한 통신 규약입니다. 주로 HTML 문서, 이미지, 비디오 등의 리소스를 전송하는 데 사용됩니다.

HTTP는 요청(Request)과 응답(Response) 구조로 작동합니다. 클라이언트가 서버에 요청을 보내면 서버는 그에 대한 응답을 반환합니다. 이 과정에서 GET, POST, PUT, DELETE 등의 메서드를 사용하여 리소스에 대한 다양한 작업을 수행할 수 있습니다.

HTTP는 상태를 유지하지 않는(Stateless) 프로토콜로, 각 요청은 독립적으로 처리됩니다. 이러한 특성 때문에 쿠키나 세션과 같은 추가적인 메커니즘을 통해 상태를 관리하며 현재는 보안이 강화된 HTTPS가 표준으로 사용되고 있습니다.

<br>

**_HTTP 상태 코드의 개념을 설명하세요_** HTTP 상태 코드는 서버와 클라이언트 간의 HTTP 통신 결과를 세자리 숫자로 표현한 응답 코드입니다. 통신 결과가 성공적이었는지, 요청 과정에 문제가 있었는지, 또는 서버 내부에서 오류가 발생했는지를 명확하게 표현하기 위해 사용되며, 100번대부터 500번대까지의 숫자를 사용합니다. **_200번대 상태 코드에 대해 설명하세요_** 200번대 상태 코드는 클라이언트의 요청이 서버에서 성공적으로 처리되었음을 나타냅니다. 뿐만 아니라, 요청 처리 결과가 응답 본문에 포함되어 있는지, 그리고 클라이언트의 요청에 의해 서버에서 특정 동작이 수행되었는지도 알 수 있습니다. 대표적으로 201 코드는 클라이언트의 POST 요청에 의해 서버에 리소스가 성공적으로 생성되었음을 의미합니다. 또한, 204 코드는 통신 결과는 성공했으나, 응답 본문은 별도로 제공하지 않는다는 의미입니다. **_300번대 상태 코드에 대해 설명하세요_** 300번대 상태 코드는 클라이언트의 요청을 다른 리소스 혹은 URL로 유도하는 역할을 합니다. 예를 들어, 304 상태 코드는 현재 요청하는 리소스가 변경되지 않았음을 의미합니다. 그렇기 때문에, 현재 클라이언트 측에 캐싱되어 있는 리소스를 그대로 재사용하면 된다고 지시하는 것이죠. **_400번대 상태 코드에 대해 설명하세요_** 400번대 상태 코드는 클라이언트 요청이 잘못되었음을 의미합니다. 뿐만 아니라, 요청이 구체적으로 어떻게 잘못되었는지도 알 수 있습니다. 예를 들어, 401 코드는 잘못된 인증 정보를 갖고 요청했음을 의미하며, 404 코드는 요청한 리소스가 서버에 존재하지 않다는 것을 의미합니다. 그 외에도, 요청 매개변수가 잘못 설정되어 있는지, 헤더가 잘못 설정되어 있는지, 또는 HTTP 메서드가 잘못되었는지, 다양한 400번대 코드를 통해 확인할 수 있습니다.  

  

**_400번대 상태 코드와 500번대 상태 코드의 차이점을 설명하세요_** 400번대 상태 코드는 클라이언트의 요청이 잘못되었음을 의미하지만, 500번대 상태 코드는 서버 오류로, 요청은 서버에 정상적으로 도달했으나, 서버 내부에서 요청을 처리하는 과정에 문제가 발생했음을 의미합니다. **_HTTP 상태 코드를 잘 지켜야 하는 이유는 무엇인가요?_** 명확한 상태 코드를 전달하면, 클라이언트측에서 어떤 종류의 에러가 발생했는지 빠르게 파악할 수 있으며, 이에 따른 적절한 처리를 할 수 있습니다. 또한, axios와 같은 Promise 기반 라이브러리는 200번대 상태 코드인 경우만 resolve로 처리하고, 나머지는 reject로 처리합니다. 즉, 실패한 처리를 200번대 코드로 응답하면, reject가 아닌 resolve로 처리되기 때문에, 디버깅이 다소 힘들어질 수 있습니다.  

<br>

### 24\. OAuth

OAuth는 사용자의 비밀번호를 공유하지 않고도 제3자 애플리케이션에 사용자 데이터에 대한 접근 권한을 부여할 수 있는 인증 프로토콜입니다. 사용자가 Google, Facebook 같은 서비스의 계정으로 다른 웹사이트나 앱에 로그인할 때 흔히 사용됩니다. OAuth는 접근 토큰을 발급하여 제한된 권한만 부여하므로, 사용자의 민감한 정보를 보호하면서도 필요한 기능을 안전하게 사용할 수 있게 해줍니다. OAuth를 활용하여 카카오톡 간편 로그인 구현을 sns 프로젝트에서 구현한 적이 있습니다.

<br>

### 25\. 쿠키, 세션스토리지, 로컬스토리지의 차이점

먼저 쿠키는 웹 클라이언트에서 사용하는 저장 수단으로, 키와 값 한쌍으로 데이터가 저장됩니다. 쿠키는 HTTP 요청 시 자동으로 헤더에 포함되어 전송되기 때문에, 주로 인증 정보와 같이 서버와의 통신에 필요한 데이터를 저장하며, 많은 용량의 쿠키가 저장되어 있을 경우, 통신 과정에서 오버헤드가 발생할 수 있기 때문에, 일반적으로 쿠기 한 개의 용량을 4KB로 정도로 제한합니다. 또한, 쿠키는 \`Max-Age\` 속성을 통해 데이터 저장 시 만료 날짜를 지정할 수 있고, \`Path\` 속성을 통해 같은 도메인 내에서도 쿠키가 전송될 URL의 범위를 설정할 수 있다는 특징이 있습니다.

**_localStorage와 sessionStorage의 공통점에 대해 설명해주세요_** localStorage와 sessionStorage는 HTML5에서 새롭게 도입된 Web Storage로, document 객체로도 접근할 수 있는 쿠키와는 달리, 자바스크립트를 통해서만 데이터 저장과 접근이 가능합니다. key, value 형태로 약 5MB까지 저장이 가능하며, HTTP 요청 시 자동으로 데이터를 전송하지 않기 때문에, 비교적 대용량의 데이터를 클라이언트 측에서 관리하고 싶을 때 사용합니다. 쿠키와는 달리 명시적으로 만료 날짜를 지정할 수 없습니다. **_localStorage와 sessionStorage의 차이점에 대해 설명해주세요_** localStorage는 탭이나 브라우저를 닫아도 데이터가 제거되지 않으며, 도메인만 동일하다면, 2개 이상의 탭이 열려 있어도 이들 간에 데이터가 공유된다는 특징이 있습니다. 반면, sessionStorage는 탭이나 브라우저가 닫히면 데이터가 자동으로 제거되며, 동일한 탭 내에서만 데이터가 유지된다는 특징이 있습니다.  

  

### **26\. 클래스형 컴포넌트와 함수형 컴포넌트의 차이**

클래스형 컴포넌트는 제가 사용해본적은 없으나, ES6 클래스를 사용하여 React.Component를 상속받아 구현하는걸로 알고 있습니다. 생명주기 메서드(componentDidMount, componentDidUpdate 등)를 통해 컴포넌트 상태를 관리하고, this 키워드로 props, state, 메서드에 접근합니다. 상태 관리를 위해 this.state와 this.setState를 사용합니다.

반면 함수형 컴포넌트는 JavaScript 함수로 구현되며, useState나 useEffect와 같은 React Hook함수들을 통해 상태 관리와 생명주기 기능을 사용합니다.

<br>

저는 주로 함수형 컴포넌트와 Hooks를 사용하여 개발해왔습니다. 함수형 프로그래밍 방식이 코드의 가독성과 재사용성을 높이고, 상태 관리가 더 직관적이라고 느꼈습니다. 현재 React 개발 트렌드도 함수형 컴포넌트 중심으로 발전하고 있어 이 방식에 집중하고 있으나, 필요하다면 클래스형 컴포넌트의 생명주기 메서드와 패턴도 빠르게 습득하여 어떤 환경에서도 효율적으로 적응하겠습니다.

<br>

### 27\. CSR과 SSR의 차이점

CSR(Client-Side Rendering)은 브라우저에서 JavaScript를 실행하여 페이지를 렌더링하는 방식입니다. CSR은 먼저 초기에 빈 HTML을 받은 후 JS 번들을 다운로드하고 실행하여 DOM을 구성합니다. 이로인해 초기 로딩 시간이 길어지며, FCP(First Contentful Paint)가 늦게 발생하고, Hydration 과정을 거쳐 인터랙티브해지기까지 TTI(Time to Interactive)가 길어 사용자가 콘텐츠를 보는 데 지연이 발생합니다. 하지만 초기 로딩 후에는 SPA 방식으로 빠른 페이지 전환이 가능합니다. 

<br>

SSR(Server-Side Rendering)은 서버에서 HTML을 완성하여 클라이언트에 전송하는 방식입니다. 초기 로드 시 완성된 HTML을 받아 FCP가 빠르게 발생하여 사용자가 콘텐츠를 빨리 볼 수 있습니다. 이후 JS가 로드되면 하이드레이션 과정을 통해 정적 HTML에 이벤트 리스너를 연결하여 인터랙티브한 웹 페이지로 전환됩니다. SEO에 유리하지만 서버 부하가 큽니다. 

<br>

### 28\. CSR과 SSR의 장단점

CSR의 장점은 초기 로딩 후 페이지 전환이 빠르고 부드러우며, 서버 부하가 적다는 점입니다. 또한 풍부한 인터랙션과 동적 경험을 제공하기 용이합니다. 반면 단점으로는 초기 로딩 시간이 길고, SEO에 불리하며, 저사양 기기나 느린 네트워크 환경에서 사용자 경험이 저하될 수 있습니다.

<br>

SSR의 장점은 초기 로딩 시 FCP가 빠르고 SEO에 유리하다는 점입니다. 사용자는 JavaScript가 완전히 로드되기 전에도 콘텐츠를 볼 수 있어 초기 사용자 경험이 좋습니다. 단점으로는 서버 부하가 크고, 페이지 전환 시 새로운 HTML을 요청해야 할 수 있어 전환 경험이 CSR보다 느릴 수 있습니다.

###   

Next.js와 같은 프레임워크는 이러한 두 방식의 장점을 결합하여, 초기 로딩은 SSR로 빠른 FCP를 제공하고, 이후 페이지 전환은 클라이언트 측 라우팅으로 SPA와 유사한 경험을 제공합니다. 또한 SSG, ISR 등 다양한 렌더링 전략을 통해 각 페이지의 특성에 맞는 최적화가 가능합니다.

<br>

### 29\. CSR에서 검색엔진 최적화 이슈가 발생하는 이유

CSR에서 SEO 이슈가 발생하는 이유는 초기 HTML이 거의 비어있고 JavaScript 실행된 후에야 콘텐츠가 생성되기 때문입니다. 대부분의 검색엔진 크롤러는 JavaScript 실행 능력이 제한적이거나 처리에 시간이 필요해, 콘텐츠를 제대로 인식하지 못합니다. 이로 인해 웹사이트 콘텐츠가 검색 결과에 제대로 노출되지 않아 트래픽 확보에 어려움이 생깁니다.

<br>

### 30\. Next.js의 렌더링 방식

**프리렌더링은**Next.js의 핵심 기능으로, 모든 페이지를 클라이언트 측 JavaScript로 렌더링하기 전에 HTML을 미리 생성합니다. 이는 더 나은 성능과 SEO를 제공합니다. 프리렌더링에는 SSR과 SSG 두 가지 형태가 있습니다.

<br>

**SSR(Server-Side Rendering)은** 요청이 있을 때마다 서버에서 HTML을 생성합니다. 항상 최신 데이터를 제공할 수 있지만, 서버에 부하가 생길 수 있습니다. 프리렌더링을 통해 전통적인 SSR보다 빠른 응답이 가능합니다.

<br>

**SSG(Static Site Generation)은** 사전렌더링 자체를 빌드 시점에 진행되어 정적으로 사이트가 만들어집니다. 매우 빠른 로딩 속도를 제공하지만, 데이터가 변경되면 재빌드가 필요합니다. 이때문에 최신데이터가 업데이트 됐다하더라도 실시간반영이 되지 않는 치명적인 단점이 존재합니다. 빌드 시 데이터를 정의하므로 대량의 데이터 처리 시 빌드 시간이 길어질 수 있습니다. 이러한 점들때메 SSR과 SSG를 교차해서 사용합니다.

블로그포스트, 제품/회사 소개페이지처럼 콘텐츠가 자주 변경되지 않으면 SSG, 대시보드, 소셜미디어 피드 등과 같이 실시간 데이터를 보여줘야하면 SSR방식이 적합합니다.

<br>

**ISR(Incremental Static Regeneration)**: SSG의 장점을 유지하면서 정기적인 업데이트를 제공합니다. revalidate 옵션으로 페이지 재생성 주기를 설정할 수 있어, 정적 페이지의 성능을 유지하면서도 데이터를 최신 상태로 유지할 수 있습니다.

<br>

### 31\. 프리렌더링을 통한 렌더링과정

Next.js에서 프리렌더링은 모든 페이지에서 필수적으로 발생하는 과정입니다. 사용자가 특정 페이지를 요청하면 서버는 해당 페이지의 HTML을 프리렌더링합니다. 이때 서버 컴포넌트는 이 단계에서 함께 렌더링됩니다.

<br>

프리렌더링된 HTML이 클라이언트로 전송되고, 브라우저는 이를 파싱하여 DOM을 구성합니다. CSS가 로드되고 적용되면 FCP(First Contentful Paint)가 발생하여 사용자에게 초기 콘텐츠가 표시됩니다. 이 시점에서 페이지는 보이지만 아직 상호작용은 불가능합니다.

<br>

다음으로 서버는 클라이언트 컴포넌트들을 번들링하여 JavaScript 파일로 클라이언트에 전송합니다. 브라우저가 JavaScript를 로드하고 실행하면 하이드레이션 과정이 진행됩니다. 이 과정에서 정적 HTML에 이벤트 리스너와 상태가 연결되어 인터랙티브한 요소로 변환됩니다.

<br>

하이드레이션이 완료되면 TTI(Time to Interactive)에 도달하여 페이지가 완전히 상호작용 가능한 상태가 됩니다. Next.js의 이러한 접근 방식은 CSR의 단점인 긴 초기 로딩 시간을 해결하면서도, 서버 컴포넌트와 클라이언트 컴포넌트를 분리하여 효율적으로 처리할 수 있게 합니다.

<br>

### 32\. URI/URL의 차이점

URI(Uniform Resource Identifier)는 인터넷에서 자원을 식별하기 위한 통합 자원 식별자입니다. 모든 웹 리소스를 고유하게 식별할 수 있는 문자열로, URL을 포함하는 상위 개념입니다.

URL(Uniform Resource Locator)은 URI의 하위 개념으로, 자원의 위치와 접근 방법을 명시합니다. 웹 브라우저에서 주로 사용하는 주소 형식으로, 프로토콜(http, https), 도메인, 경로, 쿼리 파라미터 등을 포함합니다. 

즉, URL은 자원의 위치를 나타내는 방법이고, URI는 자원을 식별하는 더 넓은 개념입니다.

<br>

### 33\. Git-flow

Git-flow는 효율적인 협업을 위한 Git 브랜칭 전략입니다. 주요 브랜치인 master(배포 코드)와 develop(개발 코드)을 중심으로, 기능 개발은 feature 브랜치에서 진행합니다. 릴리스 준비는 release 브랜치에서, 긴급 수정은 hotfix 브랜치에서 이루어집니다. 이 전략은 체계적인 버전 관리와 병렬 개발을 가능하게 합니다.

<br>

### 34\. SEO가 무엇인지/SEO최적화를 구성하는 방법

SEO(Search Engine Optimization)는 검색 엔진 최적화로, 웹사이트가 검색 엔진 결과 페이지에서 더 높은 순위에 노출되도록 최적화하는 과정입니다. 이는 웹사이트의 가시성을 높이고 유기적 트래픽을 증가시키는 데 중요합니다.

SEO 최적화 방법으로는 먼저 메타 태그(title, description)를 적절히 설정하고, 시맨틱 HTML 태그(h1, h2, article 등)를 사용하여 콘텐츠 구조를 명확히 합니다. 또한 이미지에 alt 속성을 추가하고, 모바일 친화적인 반응형 디자인을 적용합니다.

페이지 로딩 속도 개선을 위해 이미지 최적화, 코드 압축, 브라우저 캐싱을 활용하고, 사이트맵을 생성하여 검색 엔진이 페이지를 쉽게 크롤링할 수 있게 합니다. 또한, HTTPS를 사용하여 보안을 강화하는 것도 중요합니다.

<br>

### 35\. CORS

CORS는 Cross Origin Resource Sharing의 약자로, 교차 출처 리소스 공유라고도 부릅니다. SOP에 의해 제한된 교차 출처 간 리소스 공유를 허용하기 위한 방법입니다. 애플리케이션의 요구 사항이 복잡해지면서, 다른 도메인의 리소스를 활용하는 경우가 많아졌기 때문에 등장한 프로토콜로, 서버에서 CORS 관련 헤더를 설정하여 다른 도메인에서의 리소스 요청을 허용할 수 있습니다. CORS 에러는 CORS 헤더를 적절히 설정하지 않은 상태에서 교차 출처 리소스를 요청하는 경우 발생할 수 있습니다. **_SOP란 무엇인지 설명해주세요_** Same Origin Policy의 약자로, 동일 출처 정책을 의미합니다. 현재 출처와 동일한 출처의 리소스만 접근할 수 있도록 하는 정책입니다. 여기서 동일 출처란, 도메인과, 프로토콜, 포트 번호가 모두 같은 경우를 의미하며, 하나라도 다를 경우 동일 출처 정책에 의해 리소스 접근이 제한됩니다. **_SOP가 없을 경우 가능한 보안 취약점은 무엇인가요?_** 사용자 인증 정보에 해당하는 세션 ID같은 정보들이 쿠키에 포함되어 있을 수 있기 때문에 이 세션 정보를 탈취하여 Cross Site Scripting 혹은, CSRF와 같은 해킹 공격에 이용할 수 있습니다. SOP 정책을 통해 리소스를 다른 도메인에서 접근하지 못하도록 제한한다면, 이러한 해킹 공격을 어느 정도 완화할 수 있습니다. **_CORS 프로토콜이 동작하는 원리를 설명해주세요_** 서버는 응답 처리 코드에서 CORS 관련 헤더를 설정할 수 있습니다. 이 헤더를 통해 요청을 허용할 도메인과, HTTP 메서드, 그리고 요청 헤더의 종류를 정의할 수 있습니다. 이후, 브라우저에서 서버로 리소스를 요청할 때, 이 헤더에 설정한 정보와 일치하지 않는다면, 브라우저에서 CORS 에러가 발생하는 것입니다. CORS 프로토콜 스펙에서 정의한 비교적 보안적으로 민감하지 않다고 판단되는 요청들이 있는데, 이를 단순 요청이라고 칭하며, 이 요청을 제외한 모든 CORS 요청에는 실제 요청을 전송하기 전, 요청 허가를 위한 preflight 요청이 발생할 수 있습니다.  

  

**_Preflight 요청이란 무엇인지 설명해주세요_** preflight 요청은 보안적으로 민감한 CORS 요청에 대해, 실제 요청을 보내기 전에 해당 요청이 안전한지 확인하기 위해 보내는 예비 요청입니다. 브라우저에서 자동으로 실행되는 요청으로, OPTIONS 메서드를 사용하며, 서버는 이에 대해 "허용됩니다" 또는 "허용되지 않습니다"라고 응답하고, 허용된 경우에만 브라우저가 실제 요청을 보냅니다. 이 과정을 통해 허용되지 않는 요청에 대한 처리 부하를 낮출 수 있습니다. **_모든 CORS 프로토콜마다 Preflight 요청이 일어나나요?_** 보안적으로 민감하지 않은 단순 요청이거나, 이전에 응답받은 Preflight 응답이 캐싱되어 있는 경우 Preflight 요청이 일어나지 않습니다. 서버에서 Access-Control-Max-Age라는 헤더값을 초 단위로 설정할 수 있고, 이전 요청의 응답값이 아직 캐싱되어 있다면, 같은 요청에 대해서는 Preflight 요청이 일어나지 않습니다. **_단순 요청이 무엇인지 설명해주세요_** 요청의 메서드가 GET, HEAD(GET 메서드와 유사하지만 응답 본문(body)을 반환하지 않고 헤더만 반환), POST 중 하나이며, 헤더와 Content-Type이 CORS 프로토콜에서 지정한 값인 경우가 단순 요청에 해당합니다. 이 경우는 Preflight 과정을 통한 권한 조회 과정 없이 CORS 요청이 가능합니다.  

<br>

### 36\. Nginx

Nginx는 고성능 웹 서버이자 리버스 프록시 서버입니다. 정적 파일 서빙, 로드 밸런싱, 캐싱 기능을 제공하며, 특히 대규모 트래픽 처리에 효과적이며, 제 포트폴리오 프로젝트에서는 Nginx의 리버스 프록시 기능을 활용하여 방명록 서버의 CORS 정책 위반 문제를 해결했습니다. 

<br>

### 37\. SSL

SSL은 웹사이트와 브라우저 간 통신을 암호화하는 보안 프로토콜입니다. 데이터 암호화, 서버 인증, 메시지 무결성을 제공하여 중간자 공격과 데이터 도청을 방지합니다. 웹사이트에 SSL 인증서를 설치하면 HTTPS 프로토콜을 사용하게 되어 사용자에게 안전한 연결임을 알립니다.

<br>

### 38\. XSS/방어방법

XSS(Cross-Site Scripting)는 웹사이트에 악성 스크립트를 삽입하여 사용자 브라우저에서 실행되게 하는 공격입니다. 이를 통해 공격자는 쿠키 탈취, 세션 하이재킹, 피싱 등을 수행할 수 있습니다.

<br>

방어 방법으로는 사용자 입력 데이터를 출력할 때 HTML 특수문자를 이스케이프 처리하고, React와 같은 프레임워크의 자동 이스케이프 기능을 활용합니다. Content-Security-Policy 헤더를 설정하여 스크립트 실행을 제한하고, HttpOnly 플래그로 쿠키를 보호합니다. 또한 입력값 검증과 정기적인 보안 감사를 통해 취약점을 사전에 발견하고 조치해야 합니다.

<br>

### 39\. CSRF/방어방법

CSRF(Cross-Site Request Forgery)는 사용자가 자신의 의지와 무관하게 공격자가 의도한 행동을 수행하게 하는 공격입니다. 사용자가 로그인된 상태에서 악성 웹사이트에 접속하면, 해당 사이트가 사용자 모르게 정상 사이트로 요청을 보내 권한 있는 작업을 실행합니다. 

<br>

방어 방법으로는 CSRF 토큰을 사용하여 각 요청의 정당성을 검증하고, Same-Site 쿠키 속성을 설정하여 크로스 사이트 요청에 쿠키 전송을 제한합니다. 또한 중요한 작업 수행 시 사용자 재인증을 요구하고, Referer 헤더를 검사하여 요청 출처를 확인합니다. 이러한 다중 방어 전략으로 CSRF 공격을 효과적으로 방지할 수 있습니다.

<br>

### 40\. 함수형 프로그래밍이란?

함수형 프로그래밍은 순수 함수를 조합하여 소프트웨어를 구축하는 프로그래밍 패러다임입니다. 이 접근 방식은 상태 변경과 가변 데이터를 최소화하고, 함수를 일급 객체로 취급합니다. 핵심 원칙으로는 순수 함수 사용(동일 입력이면 항상 동일 출력 반환), 불변성 유지(데이터 변경 대신 새 데이터 생성) 등이 있습니다.

함수형 프로그래밍은 코드의 예측 가능성과 테스트 용이성을 높이고, 병렬 처리에 적합하며, 선언적 프로그래밍 스타일로 가독성을 향상시킵니다. JavaScript에서는 map, filter, reduce 같은 고차 함수를 통해 함수형 프로그래밍 기법을 적용할 수 있습니다.

<br>

#### 일급객체란?

일급 객체(First-class Object)는 프로그래밍 언어에서 다음과 같은 특성을 가진 객체를 말합니다:

1. 변수에 할당할 수 있음
2. 함수의 인자로 전달할 수 있음
3. 함수의 반환값으로 사용할 수 있음
4. 자료구조(배열, 객체 등)에 저장할 수 있음

<br>

### 41\. 화살표 함수와 function키워드의 차이점

먼저, 화살표 함수는 코드 블럭을 사용하지 않을 경우, return 문을 명시할 필요가 없습니다. 또한, function 키워드는 arguments 객체를 통해 함수 인자에 접근할 수 있지만, 화살표 함수는 arguments 객체를 갖지 않기 때문에, 나머지 매개 변수를 통해 함수 인자에 접근할 수 있습니다. 마지막으로, 함수 호출 방식에 따라 this의 참조가 다르게 동작하는 function 키워드와는 달리, 화살표 함수는 this가 항상 상위 스코프의 this를 참조합니다. **_왜 화살표 함수에서는 this가 항상 상위 스코프를 참조하도록 하였을까요?_** function 키워드로 정의한 함수는 호출 방식에 따라 this 바인딩이 다르게 동작하기 때문에, this 값을 예측하기 어렵다는 문제가 있습니다. 따라서, 화살표 함수에서는 this가 항상 상위 스코프를 참조하도록 개선하여, this 바인딩의 일관된 동작을 보장하고, 코드 흐름에 따라 this의 참조값을 예측하기 쉽도록 만든 것입니다. **_function 키워드 함수의 this 바인딩은 어떤 식으로 동작하나요?_** 일반적인 함수 호출의 경우는 this가 전역 객체를 가리키며, 객체의 메서드로 호출되는 경우는 해당 객체를 가리키게 됩니다. 또한, 함수가 이벤트 핸들러로써 호출되는 경우에는 이벤트가 발생한 요소를 가리킵니다. 이처럼, function 키워드로 정의한 함수는 this 바인딩의 일관성이 부족하기 때문에, ES6 이전에는 apply나 call, bind와 같은 함수를 통해 명시적으로 this 바인딩을 수행했습니다.  

<br>

### 42\. 웹펙 사용이유와 기능

웹팩은 JavaScript 모듈 번들러로, 여러 파일을 하나로 묶어 HTTP 요청을 줄이고 성능을 최적화합니다. 주요 기능으로는 모듈 번들링, CSS/이미지 등을 처리하는 로더, 번들 최적화를 위한 플러그인, 필요한 코드만 로드하는 코드 스플리팅이 있습니다. 개발 시에는 핫 모듈 리플레이스먼트(HMR)로 빠른 개발 경험을 제공하고, 프로덕션에서는 코드 압축과 트리 쉐이킹으로 번들 크기를 최적화합니다.

<br>

### 43\. Hot Module Replacement란?

Hot Module Replacement(HMR)는 웹팩의 기능으로, 개발 중인 애플리케이션의 모듈을 페이지 새로고침 없이 실시간으로 교체할 수 있게 해줍니다. 코드를 수정하면 변경된 모듈만 교체되어 애플리케이션의 상태를 유지한 채 변경사항이 즉시 반영됩니다. 이를 통해 개발자는 폼 입력값이나 스크롤 위치 같은 UI 상태를 잃지 않고 빠르게 개발할 수 있어 개발 생산성이 크게 향상됩니다.

<br>

### 44\. 트리 쉐이킹이란?

트리 쉐이킹(Tree Shaking)은 JavaScript 모듈에서 실제로 사용되는 코드만 번들에 포함시키고 사용되지 않는 코드를 제거하는 최적화 기법입니다. 이름은 나무를 흔들어 죽은 잎만 떨어뜨리는 것에서 유래했습니다. ES 모듈의 정적 구조를 분석하여 가능해진 이 기술은 웹팩 등과 같은 번들러에서 지원하며, 최종 번들 크기를 줄여 웹 애플리케이션의 로딩 속도와 성능을 향상시킵니다.

<br>

### 45\. 트랜스파일러

트랜스파일러는 프로그래밍 언어로 작성된 코드를 다른 언어 또는 다른 문법으로 변환하는 도구입니다. Babel, SWC, esbuild 같은 도구들이 이에 해당하며, 이를 통해 개발 과정에서 React의 JSX 문법이나 타입스크립트를 사용할 수 있습니다. **_컴파일러와 트랜스파일러의 차이점은 무엇인가요?_**  

컴파일러는 프로그래밍 언어로 작성된 코드를 기계어/어셈블리어, 또는 바이트 코드로 변환하지만, 트랜스파일러는 프로그래밍 언어를 또 다른 언어로 변환합니다. 혹은 프로그래밍 언어로 작성된 코드에서 최신 문법을 구형 문법으로 변환하는 역할도 수행하죠. 브라우저의 제품, 혹은 버전에 따라 문법의 지원 범위가 다르기 때문에, 애플리케이션이 다양한 브라우저에서 구동되려면 이 과정이 필요합니다. 예를 들어, 화살표 문법으로 작성된 코드는 ES6를 지원하는 브라우저에서만 실행이 가능합니다. 따라서, 이 문법을 지원하지 않는 구형 브라우저에서 이 코드가 실행되게 하려면 function 키워드로 변환해야 합니다. 이 때, 빌드 타임에서 화살표 함수를 function 키워드로 변환해주는 것이 트랜스파일러의 역할이죠. **_트랜스파일러와 폴리필은 어떤 차이가 있나요?_** 두 도구 모두 구형 브라우저 지원을 위해 사용하지만, 트랜스파일러는 빌드 타임에서 실행되는 반면, 폴리필은 런타임에 실행된다는 차이점이 있죠. 또한, 트랜스파일러는 문법만 변경하기 때문에, API 자체가 브라우저에서 지원되지 않는 경우는 폴리필을 사용해야 합니다. 예를 들어, ES6에서 도입된 API인 Promise는 기본적으로 구형 브라우저에서 사용이 불가능합니다. 트랜스파일러 또한 API의 호환성 작업은 수행하지 않죠. 이 때, 폴리필을 적용하면, 웹 애플리케이션에서 Promise 함수가 호출되었을 때, 이를 감지한 뒤, 내부적으로 다른 함수를 호출하여 사용자가 보기에는 동일한 동작으로 보이게끔 우회할 수 있습니다. 대표적으로 \`core-js\` 라는 폴리필 라이브러리가 있습니다. **_React 프로젝트에서 트랜스파일러를 사용하는 이유는 무엇인가요?_** 브라우저는 자바스크립트 엔진이 내장되어 있기 때문에, 기본적으로 표준 자바스크립트 코드만 실행이 가능합니다. 한편, React에서 컴포넌트 가독성을 높이기 위해 사용하는 JSX 문법은 표준 자바스크립트라고 볼 수 없습니다. 따라서, 빌드 타임에서 JSX 문법으로 작성된 코드를 표준 자바스크립트 코드로 변환하는 작업을 거쳐야 합니다. 동일한 원리로, 개발 과정에서 정적 타입 지원을 위해 사용하는 타입스크립트 역시 표준 자바스크립트라고 볼 수 없습니다. 개발이 완료된 이후, 브라우저에서 실행되려면 TSC라는 트랜스파일러를 통해 타입스크립트 코드를 표준 자바스크립트 코드로 변환하는 작업이 필요하죠. **_트랜스파일러가 없으면 어떻게 되나요?_** 타입스크립트 언어로 개발이 불가능하기 때문에 개발 편의성과 안정성이 현저히 낮아질 수 있습니다. 마찬가지로 React에서 JSX 문법을 사용할 수 없기 때문에, 컴포넌트 가독성이 크게 떨어질 수 있습니다.  

<br>

### 46\. 이터러블 객체

이터러블(Iterable) 객체는 반복 가능한 객체로, Symbol.iterator 메서드를 구현하여 반복문상에서 순회할 수 있는 객체를 말합니다. 이 메서드는 이터레이터(Iterator) 객체를 반환하며, 이터레이터는 next() 메서드를 통해 컬렉션의 요소를 순차적으로 접근할 수 있게 합니다.

JavaScript에서 배열, 문자열, Map, Set 등이 기본적으로 이터러블 객체이며, 사용자 정의 객체도 Symbol.iterator 메서드를 구현하면 이터러블하게 만들 수 있습니다. 이를 통해 데이터 컬렉션을 일관된 방식으로 처리할 수 있습니다.

<br>

### 47\. 제너레이터

제너레이터(Generator)는 함수의 실행을 중간에 멈추고 재개할 수 있는 특별한 JavaScript 함수입니다. function\* 키워드로 선언하며, yield 표현식을 사용해 값을 반환하고 실행을 일시 중지합니다. 제너레이터 함수를 호출하면 이터레이터 객체가 반환되어 next() 메서드로 실행을 제어할 수 있습니다.

제너레이터는 비동기 프로그래밍, 데이터 스트림 처리, 무한 시퀀스 생성 등에 유용하며, 복잡한 상태 관리 없이 이터러블한 객체를 쉽게 구현할 수 있게 해줍니다. 메모리 효율적인 데이터 처리가 가능하여 대용량 데이터를 다룰 때 특히 유용합니다.

<br>

### 48\. 클로저

자바스크립트는 렉시컬 스코프 규칙을 따르기 때문에 우선 변수가 선언되는 곳에서 스코프가 지정이 됩니다. 이때문에, 일반적인 방식으로는 함수 선언문 밖에서의 함수 스코프에 접근할 수 없습니다. 이를 보완하기 위한 방법이 바로 클로저 함수이며, 클로저 함수는 스코프가 상위 함수의 스코프를 참조하는 함수를 return하는 방식으로 구동됩니다. React의 useState가 대표적인 클로저 사용 방식의 예입니다.

<br>

### 49\. this

JavaScript에서 this는 함수가 호출되는 방식에 따라 동적으로 결정됩니다. 기본적으로 this는 함수를 호출한 객체를 가리킵니다.

일반 함수 호출에서 this는 전역 객체(브라우저에서는 window, Node.js에서는 global)를 가리킵니다. 객체의 메서드로 호출될 때는 해당 객체를 가리키고, new 키워드로 생성자 함수를 호출할 때는 새로 생성된 인스턴스를 가리킵니다.

this 바인딩을 명시적으로 제어하기 위해 call(), apply(), bind() 메서드를 사용할 수 있습니다. 화살표 함수는 자신만의 this를 가지지 않고, 정의된 시점의 상위 스코프의 this를 그대로 사용합니다.

이러한 차이로 인해 객체의 메서드나 생성자 함수로는 function 키워드 함수가 적합하고, 콜백 함수나 이벤트 핸들러에서는 상위 스코프의 this를 일관되게 유지해야 할 때 화살표 함수가 유용합니다.

<br>

### 50\. 실행컨텍스트

실행 컨텍스트는 JavaScript 코드가 실행되는 환경을 추상화한 개념입니다. 코드 실행에 필요한 변수, 함수 선언, this 바인딩, 스코프 체인 정보를 담고 있습니다. JavaScript 엔진은 코드 실행 시 실행 컨텍스트를 생성하고 스택에 쌓아 관리합니다. 전역 컨텍스트가 먼저 생성되고, 함수 호출 시 함수 컨텍스트가 생성됩니다. 

<br>

### 51\. 가비지컬렉터와 동작방식

가비지 컬렉터는 더 이상 필요하지 않은 메모리를 자동으로 해제하는 시스템입니다. 주요 동작 방식으로 객체의 참조 수를 세어 0이 되면 해제하는 참조 카운팅과 루트에서 도달 가능한 객체를 마크하고 나머지 해제하는 마크 앤 스윕이 있습니다. 예를 들어, 함수가 실행될 때 지역 변수가 메모리에 할당되고, 함수 실행이 완료되면 해당 변수는 더 이상 접근할 수 없게 됩니다. 이때 가비지 컬렉터는 이 변수를 "도달 불가능"으로 판단하고 메모리에서 해제합니다. 이처럼 가비지 컬렉터는 더 이상 접근할 수 없는 객체를 자동으로 감지하고 메모리를 회수하여 메모리 누수를 방지합니다.

<br>

### 52\. 스코프 

스코프란, 변수나 함수의 유효 범위를 의미합니다. 즉, 특정 변수나 함수를 어느 위치에서 참조할 수 있는 지를 나타내며, 만약 스코프에서 벗어난 위치에서 참조할 경우 Reference Error가 발생합니다. 자바스크립트의 스코프는 크게 전역 스코프와 로컬 스코프로 나눌 수 있으며, 이들 모두 렉시컬 스코프 규칙에 따라 결정됩니다. 로컬 스코프는 다시 함수 스코프와 코드 블록 스코프로 나눌 수 있는데, let과 const로 정의한 변수만 코드 블록 스코프를 가질 수 있습니다. **_렉시컬 스코프란 무엇인가요?_** 렉시컬 스코프란, 변수가 어디에 정의되었는지에 따라 스코프가 결정되는 메커니즘을 의미하며, 정적 스코프라고 부르기도 합니다. 이는 코드가 작성된 위치에 따라 변수의 유효 범위가 결정된다는 뜻입니다. 또한, 함수가 중첩된 경우 내부 함수는 외부 함수의 변수를 참조할 수 있지만, 외부 함수는 내부 함수의 변수를 참조할 수 없습니다. **_자바스크립트에서 변수를 참조하는 과정을 설명해주세요_** 자바스크립트는 함수가 실행될 때마다 메모리 상에 실행 컨텍스트를 생성합니다. 이 실행 컨텍스트 안에는 렉시컬 환경이 존재하는데, 여기에 현재 스코프에서 선언한 모든 변수와 함수들이 저장되어 있는 환경 레코드가 존재합니다. 또한, 현재 환경에서 찾지 못한 변수를 상위 스코프에서 찾기 위해, 상위 스코프를 가리키는 외부 렉시컬 환경 참조도 갖고 있죠. 이를 통해, 코드 상에서 변수나 함수를 참조하면, 먼저 현재의 환경 레코드에서 찾아보고, 없을 경우 외부 렉시컬 환경 참조를 통해 상위 스코프를 참조하게 됩니다. 이런 식으로 모든 상위 스코프를 탐색했는데도 찾지 못할 경우, 전역 스코프까지 올라가며, 여기서도 찾지 못하면 Reference Error를 발생시킵니다.  

<br>

### 53\. 호이스팅

호이스팅이란, 변수와 함수의 선언문이 해당 스코프의 최상단으로 끌어올려지는 현상이다. 이때문에 변수와 함수가 초기화되기 전에 접근할 수 있는 현상이 발생한다. 단, es6에서 등장한 방식인 let과 const는 호이스팅은 되지만 초기화되기 전엔 접근할 수 없다. 

<br>

**_변수와 함수 호이스팅이 동일하게 동작하는가?_**

<br>

아닙니다. 변수는 선언만 호이스팅되지만, 함수는 선언과 초기화 모두 호이스팅됩니다. 이러한 특성으로 변수는 초기화 전 참조할 경우 undefined가 나오지만, 함수는 초기화 전에 호출해도 정상적으로 호출이 가능합니다. 

<br>

**_왜 변수와 달리 함수만 초기화 과정까지 호이스팅 되는가?_**

function 키워드로 선언한 함수는 선언과 초기화, 할당 단계가 내부적으로 동시에 진행되기 때문입니다. 변수는 선언단계와 초기화 단계가 내부적으로 분리되어 두단계에 걸쳐서 실행됩니다. 

<br>

**_왜 let과 const로 선언한 변수는 초기화전에 접근할 수 없도록 막았는가?_**

<br>

코드의 예측 가능성을 높이기 위해 TDZ(Temporal Dead Zone)개념을 도입하여  호이스팅 현상으로 인해, 초기화되지 않은 변수를 개발자가 참조할 수 없도록 하기 위해서입니다. 사실호이스팅 현상은 자바스크립트 개발 과정에서 실수로 생긴, 일종의 버그이기 때문입니다. 

<br>

**_자바스크립트는 인터프리터 언어인데 어떻게 호이스팅 현상이 일어날 수 있는지?_**

<br>

일반적으로 알고 있는 인터프리터의 개념과는 달리, 자바스크립트 엔진은 파싱과 실행이라는 두 단계를 거치게 됩니다. 호이스팅이 처리되는 파싱 단계에서는 호이스팅 뿐만 아니라 구문트리(AST)와 실행컨텍스트를 생성하는 작업도 함께 수행됩니다. 

구문 트리(AST, Abstract Syntax Tree)는 **코드를 계층적 트리 구조로 표현한 자료구조**입니다.  
자바스크립트를 비롯한 대부분의 프로그래밍 언어에서 **코드를 실행하기 전에 분석(파싱)하는 과정에서 생성**됩니다.  

<br>

### 54\. 라이브러리와 프레임워크의 차이

라이브러리는 개발자가 필요할 때 호출하여 사용하는 도구 모음입니다. 개발자가 흐름을 제어하고 필요한 기능만 선택적으로 가져와 사용할 수 있어 자유도가 높습니다. React가 대표적인 라이브러리로, 개발자가 언제 어떻게 사용할지 결정합니다.

<br>

반면 프레임워크는 전체적인 구조와 규칙을 자체문법을 통해 제공하며, 개발자는 그 안에서 코드를 작성합니다. 프레임워크가 프로그램의 흐름을 제어하고 개발자는 정해진 틀 안에서 필요한 부분을 구현합니다. Next.js, Angular, Vue.js 등이 프레임워크에 해당하며, 파일 구조, 라우팅 방식 등이 미리 정의되어 있습니다.

<br>

### 55\. 어떤 프레임워크를 사용하여 개발했나요? 왜 그 프레임워크를 선택했나요?

저는 주로 Next.js를 사용하여 개발하고 있습니다. 처음에는 프레임워크 대신 시장 점유율이 높고 트렌디한 React 라이브러리를 사용했지만, CSR 방식의 초기 로딩 속도 문제와 SEO 최적화 한계를 경험했습니다.

<br>

Next.js는 SSR과 CSR을 결합한 방식으로 이러한 문제점들을 효과적으로 해결해주어 큰 매력을 느꼈습니다. 특히 페이지별로 최적의 렌더링 방식(SSR, SSG, ISR)을 선택할 수 있는 유연성이 큰 장점이었습니다.

<br>

또한 React는 라이브러리로서 자유도가 높지만, 때로는 그 자유도가 오히려 혼란을 가져올 수 있었습니다. Next.js는 프레임워크로서 어느 정도 정해진 구조와 원칙이 있어 체계적으로 개발을 진행하는 저에게 더 적합했습니다. 파일 기반의 편리한 라우팅, API 라우트, 이미지 최적화 등 개발 생산성을 높여주는 기능들도 Next.js를 선택한 중요한 이유입니다.

<br>

### **56\. "==" 와 "==="의 차이는 무엇인가요?**

"=="는 동등 연산자로, 두 값을 비교할 때 형변환을 수행합니다. 즉, 비교하는 값의 데이터 타입이 다르더라도 자동으로 형변환을 수행한 후에 비교합니다. 이러한 형변환은 때로 예측하지 못한 결과를 초래할 수 있으므로, "=="를 사용할 때는 조심해야 합니다. "==="는 일치 연산자로, 두 값이 데이터 타입과 값이 모두 같은지 비교합니다. 따라서 "==="를 사용하여 깊은비교를 통해 형변환 없이 정확한 값을 비교할 수 있습니다. 이러한 일치 연산자를 사용하는 것이 더 안전하고 예측 가능한 결과를 얻을 수 있습니다.

<br>

### 57\. Storybook

스토리북을 따로 사용해본적은 없으나, 스토리북(Storybook)은 UI 컴포넌트 개발을 위한 도구로, 개별 컴포넌트의 기능과 상태를 다양한 시나리오로 테스트하고, 문서화하여 관리할 수 있는 환경을 제공합니다. 이를 통해 UI 개발자와 디자이너는 컴포넌트의 독립적인 테스트와 문서화를 통해 작업 효율성과 코드 품질을 향상시킬 수 있습니다.

<br>

### **58\. Flex와 Grid의 차이점에 대해서 설명해보세요.**

Flex는 주로 단일 축 방향의 레이아웃을 구성하는 데 사용되며, 주로 수평 방향으로 레이아웃을 정렬합니다. Grid는 2차원 그리드 시스템을 구성하는 데 사용되며, 수평과 수직 방향으로 모두 레이아웃을 정렬할 수 있습니다. Flex는 아이템들의 크기가 자유로워 유동적으로 변할 수 있습니다. 반면에 Grid는 아이템들의 크기를 미리 정의하여 각 셀의 크기를 일정하게 유지합니다. Flex는 유동적인 레이아웃 변화를 구성하기 적합합니다. 반면에 Grid는 미리 정의된 2차원 그리드 구조를 유지하기 때문에 레이아웃 변화가 적은 경우에 적합합니다.

<br>

### 59\. 절차지향과 객체지향언어의 차이 

**절차지향 프로그래밍**은 프로그램을 순차적인 처리 과정으로 바라보는 방식입니다. 데이터와 함수가 분리되어 있으며, 함수가 데이터를 처리하는 형태로 프로그램이 구성됩니다. C언어가 대표적인 절차지향 언어입니다. 간단한 프로그램에 적합하지만, 규모가 커지면 코드 관리가 어려워질 수 있습니다.

**객체지향 프로그래밍**은 데이터와 그 데이터를 처리하는 메서드를 하나의 객체로 묶어 관리하는 방식입니다. 캡슐화, 상속, 다형성, 추상화라는 핵심 개념을 통해 코드의 재사용성과 유지보수성을 높입니다. Java, C++, Python 등이 객체지향 언어에 해당합니다.

<br>

즉, 객체지향은 대규모 프로젝트에서 코드의 재사용성과 확장성을 높이는 데 유리하며, 데이터를 중심으로 동작을 정의하여 현실의 개념을 코드로 표현하기 쉬운 방식입니다.

절차지향은 상대적으로 구조가 단순하고 작은 규모의 프로그램이나 빠른 실행 속도가 중요한 경우에 유리할 수 있습니다. 하지만 코드가 복잡해질수록 유지보수가 어려워질 수 있습니다.

<br>

## **내 이력서/프로젝트 기반 질문**

**Animated Outlet에 대하여** 

framer motion의 animatePresence는 고유한 식별자(key)와 직계자식만을 검사해준다. 이 때문에 우리는 useOutlet이라는 훅함수를 사용하여, React의 cloneElement속성을 통해 기존의 Outlet과 똑같은 역할을 해주는 요소를 복제하여 해당 복제본을 animatePresence로 감싸주고 key를 독립적으로 주기 위해 useLocation을 활용하여 location의 pathname으로 키를 부여해줘야한다. 

<br>

Outlet은 실제로 라우팅 변동이 일어난 사항을 감지하지 못한다. 이때문에 useOutlet()을 사용하여 구현을 해야한다. useOutlet은 렌더링된 컴포넌트 그 자체를 반환하기 때문이다. 또한 cloneElement를 통해서 고유한 키를 실제로 부여받을 수 있게 함으로써 animatePresence가 작동되게끔해야함. Outlet은 자식 컴포넌트를 렌더링하긴하지만, animatePresence는 명시적으로 key가 바뀌거나 컴포넌트 구조가 바뀌어야한다. useOutlet으로 만약 컴포넌트가 존재한다면 클로닝된 요소를 반환하여 올바르게 구현되도록 하면된다.

## 인성면접 예상 공통질문

<br>

1. 프론트엔드를 고른 이유

<br>

프론트엔드 개발을 선택한 이유는 제 배경과 관심사가 자연스럽게 융합된 결과입니다. 저는 고등학교 시절 미대 입시를 준비하며 시각디자인과를 희망했던 경험이 있어 디자인적 감각과 시각적 표현에 대한 이해가 있습니다. 현재는 컴퓨터공학을 전공하고 있지만, 이전의 디자인 경험을 살릴 수 있는 웹페이지의 얼굴이라 할 수 있는 프론트엔드 개발에 자연스럽게 끌렸습니다. 포트폴리오 프로젝트에서 차별화된 UI/UX를 구현할 때 이러한 배경이 큰 도움이 되었고, 기술적 구현과 시각적 디자인의 균형을 맞추는 프론트엔드 개발이 제게 가장 적합하다고 느꼈습니다.

<br>

2. 자신이 가장 잘 설명할 수 있는 것 하나 설명

<br>

React의 가상 DOM(Virtual DOM) 작동 방식을 가장 잘 설명할 수 있습니다. 가상 DOM은 실제 DOM의 가벼운 복사본으로, React가 UI 변경사항을 효율적으로 처리하는 핵심 메커니즘입니다. 상태가 변경되면 React는 먼저 가상 DOM에 새로운 UI를 렌더링하고, 이전 가상 DOM과 비교(Diffing)하여 실제로 변경된 부분만 식별합니다. 그 후 변경된 부분만 실제 DOM에 적용(Reconciliation)하여 불필요한 DOM 조작을 최소화합니다. 이 과정을 통해 React는 성능을 최적화하면서도 선언적인 UI 개발 방식을 제공합니다.

<br>

3. 개발이 적성에 잘 맞는지?

<br>

네, 개발은 제 적성에 매우 잘 맞는다고 생각합니다. 제가 가진 문제 해결 능력과 논리적 사고방식이 개발 작업에 자연스럽게 적용되는 것을 느낍니다. 특히 프론트엔드 개발은 제 디자인 감각과 기술적 구현 능력을 함께 활용할 수 있어 더욱 흥미롭게 느껴집니다.

개발 과정에서 마주치는 문제들을 해결해 나가는 과정이 저에게는 퍼즐을 푸는 것처럼 즐겁고, 코드를 통해 제가 상상한 것을 실제로 구현해내는 성취감이 큽니다. 또한 지속적으로 새로운 기술을 배우고 적용하는 과정에서 성장하는 느낌을 받을 때 개발자로서의 길을 잘 선택했다고 확신합니다.

물론 때로는 어려운 버그와 씨름하며 좌절감을 느낄 때도 있지만, 그런 문제를 해결했을 때의 기쁨이 더 크기 때문에 개발이 제 적성과 잘 맞는다고 생각합니다.

<br>

4. 왜 개발을 시작했는지?

<br>

저는 어릴 때부터 컴퓨터와 기계 다루는 것을 좋아해서 고등학교까지 프로그래머를 꿈꿔왔습니다. 하지만 고등학교에서 수학의 벽을 느끼고 제가 더 잘할 수 있는 미대 준비로 방향을 바꿨습니다. 그러나 수능 결과가 좋지 않아 미대에 진학하지 못했고, 결국 제가 원래 희망했던 개발자의 길을 가기 위해 컴퓨터 공학과에 진학하게 되었습니다.

대학에서 개발 공부를 시작했고, 특히 부트캠프에서는 실무적인 개발을 배울 수 있어 정말 흥미롭게 공부했습니다. 무엇보다 개발을 통해 실제 서비스를 만들어냈을 때의 성취감과 기쁨은 말로 표현하기 어려울 정도로 큽니다.

이런 경험들을 통해 개발이 제가 진정으로 즐기고 잘할 수 있는 분야라는 확신을 갖게 되었습니다.

<br>

5. 압박감이 클 때 어떻게 일하는지?

<br>

압박감이 클 때, 저는 체계적인 접근 방식으로 대응합니다. 우선 전체 업무를 작은 단위로 분해하고 우선순위를 설정합니다. 가장 중요하고 시급한 작업부터 처리하는 방식으로, 할 일 목록을 작성하고 각 항목의 완료 예상 시간을 설정해 계획을 세웁니다. 예를들어, 팀 프로젝트에서 기한이 임박했을 때 저는 먼저 팀원들과 빠른 회의를 통해 남은 작업을 파악하고 각자의 역할을 명확히 했습니다. 제가 직접 추가 작업을 맡아 야간에 개발하며 팀을 이끌었고, 문제가 생긴 부분은 팀원들과 페어 프로그래밍으로 해결했습니다.  결과적으로 이런 체계적인 접근과 팀워크를 통해 마감 기한 내에 프로젝트를 성공적으로 완료할 수 있었습니다.

<br>

6. 개발하면서 우선순위로 생각하는것?

<br>

개발할 때 가장 우선시하는 것은 사용자 경험입니다. 아무리 기술적으로 뛰어난 코드라도 사용자가 불편함을 느끼면 의미가 없다고 생각합니다. OTT 프로젝트에서 영화 데이터 로딩 중 스켈레톤 UI를 적용하여 사용자가 로딩 시간을 덜 답답하게 느끼도록 한 것이 그 예입니다. 포트폴리오 프로젝트에서 커스텀 커서와 404 페이지를 구현한 것도 이러한 사용자 경험을 향상시키기 위함이었습니다. 

<br>

7. 전공자인데 부트캠프를 추가로 들은 이유가 있나요?

<br>

컴퓨터공학을 전공하고 있지만, 2학년까지 배운 이론적 지식만으로는 실무에서 바로 활용할 수 있는 역량이 부족하다고 판단했습니다. 특히 병역특례를 준비하는 상황에서 더 실질적인 개발 경험과 최신 기술 스택을 빠르게 습득할 필요가 있었습니다. 대학에서는 자료구조, 알고리즘 등 기본 개념을 배웠지만, 부트캠프에서는 React, Next.js 등 현업에서 실제 사용되는 기술과 협업 경험을 쌓을 수 있었습니다. 이러한 실무 중심의 학습을 통해 회사에 입사해 즉시 기여할 수 있는 개발자로 성장하고자 부트캠프를 선택했습니다.

<br>

8. 회사와 부트캠프의 차이가 뭐라고 생각하나요?

<br>

부트캠프는 체계적인 커리큘럼을 통해 기초부터 실무 기술까지 단기간에 습득하는 교육 환경인 반면, 회사는 실제 비즈니스 가치를 창출하는 실전 환경이라고 생각합니다. 부트캠프에서는 다양한 기술을 폭넓게 경험하고 개인 성장에 집중할 수 있지만, 회사에서는 특정 도메인의 깊은 이해와 팀 협업을 통한 제품 개발이 중요합니다. 또한 부트캠프는 오류가 허용되는 학습 공간이지만, 회사는 책임감과 결과물의 품질이 중요시됩니다. 

<br>

9. 가장 좋아하는 사람이 누군지?

<br>

제가 가장 좋아하고 존경하는 사람은 아버지입니다. 아버지는 저와 전혀 다른 분야인 마케팅 쪽에서 일하시며, 호텔의 회원관리 및 매니지먼트 업무를 담당하고 계십니다. 높은 연령에도 불구하고 매일 야근하시면서도 가족에게 지친 내색 한 번 하지 않으시고, 홀로 가정 경제를 책임지시는 모습이 정말 존경스럽습니다. 이런 아버지의 책임감과 헌신적인 태도는 제가 개발자로서 일할 때도 큰 영감이 되며, 어떤 어려움이 있어도 끝까지 책임을 다하는 자세를 배우게 해주셨습니다.

제출한 서류를 바탕으로 내 경험과 업무 역량에 관한 질문을 주로 낼 예정

  

1. 간단한 자기소개

<br>

안녕하세요. 신입 병역특례 프론트엔드 개발자 포지션에 지원한 전진우입니다. 저는 사용자 중심의 웹 경험 구현에 깊은 관심을 가지고 있으며, React, TypeScript, Next.js를 중심으로 최신 프론트엔드 기술 스택을 꾸준히 연마하고 다양한 팀 프로젝트에서 PM 경험과 기술적 문제 해결 능력을 쌓았습니다. 

저는 문제를 포기하지 않고 끝까지 해결하는 끈기와 팀원들과의 적극적인 지식 공유를 통해 함께 성장하는 과정에서 큰 보람을 느낍니다.  팀스파르타의 교육 플랫폼 개선에 기여하고 "와우하게, 진정성있게"라는 핵심 가치를 실현하는 데 동참하고 싶습니다.  특히 금요일 프론트엔드 지식회와 같은 팀스파르타의 활발한 스터디 문화에 적극 참여하여 지속적인 성장을 추구하며, 동료들과 함께 발전하는 개발자가 되겠습니다.

2. 지원동기 

<br>

팀스파르타에 지원하게 된 가장 큰 이유는 교육 플랫폼을 통해 사람들의 성장을 돕는 회사의 미션에 깊이 공감하기 때문입니다. 내일배움캠프의 88%라는 높은 완주율은 질 높은 교육과 체계적인 커리큘럼을 보여주는 지표로, 이러한 가치 있는 서비스 개발에 참여하고 싶습니다.

팀스파르타의 핵심가치인 "빠르게, 와우하게, 진정성있게"는 제 개인적인 가치관과 일치합니다. 특히 "와우하게"라는 가치는 포트폴리오 개발 시 차별화된 레이아웃과 인터렉션을 추구했던 저의 접근 방식과 맞닿아 있습니다. 또한 금프지와 같은 팀스파르타의 활발한 스터디 문화, 도서 구매 무제한, 자사 교육 무제한 등과 같은 복지는 지속적인 성장을 추구하는 저에게 큰 매력입니다. 프론트엔드 개발자로서 대규모 트래픽을 관리하는 내일배움캠프 플랫폼 개발에 참여하여 기술적 역량을 키우고, 다른 개발자들의 성장을 돕는 의미 있는 일에 기여하고 싶어 지원하게 됐습니다.

3. 팀스파르타에 들어온다면 어떤 업무를 하고 싶은지

<br>

 테스트 주도 개발 방식을 적극 수용하여 안정적인 프로덕트 개발에 기여하고 싶습니다. 테스트 케이스를 먼저 상정하고 자동화하는 과정을 통해 코드의 신뢰성을 높이고, 지속적인 리팩토링이 가능한 환경을 구축하는 데 동참하겠습니다.

또한, 대규모 트래픽 관리와 성능 최적화에 참여하고 싶습니다. 내일배움캠프와 같은 대규모 교육 플랫폼은 동시 접속자가 많을 수 있어 안정적인 서비스 제공이 중요합니다. 코드 스플리팅, 지연 로딩, 메모이제이션 등의 최적화 기법을 적용하고, Next.js와같은 프레임워크를 통한 서버 사이드 렌더링과 정적 생성을 적절히 활용하여 로딩 속도를 개선하는 데 기여하고 싶습니다.

4. 이전에 내가 했던 업무에 대한질문(딱히 없지만 그나마가 hr골든캐피탈 아닐까?)

<br>

**Q: 아마존 코리아 프로젝트에서 팀원 이탈 상황을 어떻게 극복했나요?**

A:

메인 페이지 담당 팀원이 갑자기 이탈했을 때, 프로젝트 매니저로서 우선순위를 재설정하고 직접 메인 페이지 개발을 맡았습니다. HTML, SCSS, JavaScript만으로 핵심 기능부터 구현하는 전략을 세우고 야간 시간을 활용해 추가 작업을 진행했습니다. 결과적으로 기한 내에 프로젝트를 완성했고, 위기 상황에서의 문제 해결 능력을 키울 수 있었습니다.

<br>

<br>

**Q: OTT 프로젝트에서 Next.js의 서버 사이드 렌더링을 어떻게 활용했나요?**

A:

영화 상세 페이지의 로딩 속도와 SEO 최적화를 위해 Next.js의 SSR을 활용했습니다. getServerSideProps로 서버에서 영화 데이터를 미리 가져오고, 병렬 라우팅으로 상세 정보, 리뷰, 유사 영화를 동시에 로드했습니다. 이를 통해 사용자 경험을 향상시키고 SSR과 CSR의 장단점을 실제 프로젝트에서 경험할 수 있었습니다.

<br>

<br>

**Q: 포트폴리오 프로젝트에서 성능 최적화를 위해 어떤 노력을 했나요?**

A:

커스텀 커서와 애니메이션 구현 과정에서 React.memo와 useCallback을 활용해 불필요한 리렌더링을 방지했습니다. Zustand로 커서 상태를 전역 관리하고, 커스텀 AnimatedOutlet 컴포넌트로 React Router와 Framer Motion을 효과적으로 통합했습니다. 이 과정에서 이벤트 핸들링과 상태 관리 최적화 기법의 중요성을 실제로 체감했습니다.

<br>

5. 주변지인들은 나를 어떻게 생각하는가/친한 친구가 자신을 소개한다면 뭐라고 할것인지?

<br>

직접 지인들의 평가를 말하자니 부끄럽지만, 친구들은 저를 사려 깊고 책임감 있는 사람으로 평가하며, 맡은 일에 대한 성실함과 환경 적응력을 강점으로 꼽습니다. 이러한 특성은 PM으로서 체계적인 일정 관리와 업무 분배로 프로젝트를 성공적으로 이끌고, 팀원 이탈 같은 위기 상황에서도 책임감 있게 대응한 경험에서 뒷받침되는 것 같습니다. 이러한 성향은 교육 서비스를 제공하는 팀스파르타에서 중요한 책임감과 체계적인 업무 수행 능력으로 팀에 기여할 수 있는 강점이라고 생각합니다.

6. 취미는 무엇이고 스트레스를 어떻게 해소하는지?

<br>

저의 주요 취미는 키보드 수집 및 조립입니다. 개발자로서 하루 종일 키보드를 사용하는 직업의 특성상, 좋은 키보드에 대한 관심이 자연스럽게 생겼습니다. 다양한 스위치 타입과 키캡의 조합, 타건감의 차이를 경험하는 것이 큰 즐거움입니다. 특히 타자 연습을 통해 새로운 키보드의 감각을 익히는 과정도 좋아해서, 개발 작업과 취미가 시너지를 이루고 있습니다.

키보드는 조립할때 하우징 선택부터 스위치 윤활 작업, 스테빌라이저 튜닝 등등 세세한 과정을 직접 진행하며 자신만의 완벽한 타건감을 찾아가는 과정이 마치 코드를 최적화하는 것과 비슷한 만족감을 줍니다. 이런 세밀한 작업을 통해 인내심과 집중력도 기를 수 있어 개발 업무에도 긍정적인 영향을 미치고 있습니다.

<br>

7. 리엑트의 가상돔을 개발을 아예 모르는 친구에게 설명한다면?

<br>

웹페이지는 여러 요소들로 구성되어 있는데, 이것을 DOM이라고 생각하면 돼요. 예를 들어 버튼, 텍스트, 이미지 같은 것들이죠.

일반적인 웹사이트에서는 무언가 변경될 때마다 전체 페이지를 다시 그려요. 마치 메모장에 글을 쓰다가 한 글자만 바꾸려고 해도 전체 종이를 버리고 새 종이에 처음부터 다시 쓰는 것과 같아요. 이건 매우 비효율적이죠.

리액트의 가상 DOM은 이 문제를 해결해요. 가상 DOM은 실제 화면에 보이는 것의 '임시 복사본'이라고 생각하면 됩니다.

쉽게 설명하자면 변경 사항이 생기면 리액트는 먼저 이 임시 복사본에 변화를 적용해 보고, 이전 상태와 비교해서 "아, 이 버튼의 색상만 바뀌었네!"라고 파악합니다. 그 후 실제 화면에는 그 버튼의 색상만 업데이트하는 겁니다.

마치 친구와 함께 그림을 그리는데, 친구가 "저기 구름 부분만 조금 더 밝게 해볼까?"라고 제안할 때, 전체 그림을 다시 그리지 않고 구름 부분만 수정하는 것과 같습니다. 이렇게 하면 웹페이지가 훨씬 빠르게 반응하고 사용자 경험이 좋아집니다.

<br>

9. 내 활동이력에서 가장 인상 깊었던 부분은?

<br>

제 활동 이력에서 가장 기억에 남는 것은 아마존 코리아 프로젝트에서 보여준 위기 대응 능력과 리더십입니다. 프로젝트 중반에 메인 페이지 담당 팀원이 갑자기 이탈했을때, 프로젝트 매니저로서 빠르게 상황을 판단하고 우선순위 설정과 SCSS활용으로 기한내에 두 페이지를 동시에 완성하며 대응한 경험이 가장 기억에 남습니다.

이 경험을 통해 문제 해결 능력, 시간 관리 능력, 그리고 압박 상황에서의 의사결정 능력을 키울 수 있는 소중한 기회였습니다. 

또한 이 과정에서 팀원들과의 소통과 협업의 중요성을 깊이 이해하게 되었고, 이후 프로젝트에서도 이러한 경험을 바탕으로 더 효과적인 팀워크를 구축할 수 있었습니다. 

<br>

10. 나의 강점, 약점

<br>

제 강점은 성실함과 끈기, 그리고 지속적인 성장 추구입니다. 국비학원 과정에서 유일하게 개근상을 받을 정도로 지각 없이 성실하게 임하며, 문제 해결 시 포기하지 않고 끝까지 해결책을 찾아내는 끈기가 있습니다. 새로운 기술스택을 배우는걸 두려워하지 않고 오히려 즐기며, 이러한 성향은 개발 과정에서 마주치는 복잡한 문제들을 해결하는 데 큰 도움이 됩니다.

약점은 처음에 낯을 가리는 성향입니다. 하지만 이를 극복하기 위해 GS25, 메가박스, 청자다방 등 다양한 아르바이트 경험을 통해 적극적으로 사회성을 키워왔습니다. 특히 고객 응대가 많은 서비스직 경험을 통해 의사소통 능력을 향상시켰고, 아마존 프로젝트때 PM도 맡을정도로 이제는 새로운 환경에서도 빠르게 적응하고 팀원들과 효과적으로 협업할 수 있습니다.

<br>

11. 빠르게, 와우하게, 진정성있게 일을 처리햇던 경험이 있는지

<br>

제 포트폴리오 프로젝트 완성 예상 일정이 촉박해지자 "빠르게" 우선순위를 설정하고 핵심 기능부터 구현하는 전략으로 대응했습니다. 동시에 "와우하게" 차별화된 경험을 제공하기 위해 멀티페이지 디자인과 페이지 전환 애니메이션, 연결 리스트 기반 방명록 시스템을 구현했습니다. 또한 "진정성있게" 사용자 경험을 고려해 커스텀 커서를 적용하고 일반적으로 포트폴리오 페이지에는 없는 404 페이지를 구현해 사용자가 혼란을 겪지 않도록 했습니다. 이러한 세심한 배려로 방문자들로부터 "일반적인 포트폴리오와는 다른 사용자 중심의 경험"이라는 긍정적 피드백을 받았습니다.

<br>

12. 사용해본 도구, 주력스킬, 앞으로의 계획 / 앞으로의 포부

<br>

현재는 주로 React, TypeScript, Next.js를 활용한 프론트엔드 개발에 집중하고 있으며, Firebase와 MongoDB를 통한 백엔드 연동 경험도 보유하고 있습니다. 특히 React의 컴포넌트 기반 아키텍처와 상태 관리(Zustand, Recoil)에 강점이 있으며, Next.js의 SSR을 활용한 성능 최적화에도 관심이 많습니다. 앞으로는 프론트엔드에 그치지 않고 Node.js, Express 등 백엔드 기술을 더욱 깊이 학습하여 프론트에 그치지 않고 나아가 풀스택 개발자로 성장하고 싶습니다. 

<br>

13. 최근에 공부하고 있는 기술

<br>

최근에는 Next.js 14의 App Router와 서버 컴포넌트(RSC)를 중점적으로 공부하고 있습니다. 특히 서버 컴포넌트와 클라이언트 컴포넌트의 효율적인 분리 전략과 데이터 페칭 최적화 방법에 집중하고 있습니다. 예를 들어, 사용자 프로필 페이지에서 프로필 정보를 표시하는 부분은 서버 컴포넌트로 구현하여 SEO 최적화와 초기 로딩 속도를 개선하고, 프로필 편집 기능과 같은 인터랙티브한 부분은 클라이언트 컴포넌트로 분리하는 방식을 실험하고 있습니다. 

<br>

14. 자신있는 개발기술을 비전공자에게 설명하는 관점에서 설명해주세요

<br>

리액트는 웹사이트를 만드는 도구인데, 레고 블록으로 집을 짓는 것과 비슷해요. 일반적인 웹사이트 제작은 매번 전체 집을 다시 지어야 하는 방식이라면, 리액트는 필요한 블록만 교체할 수 있게 해줍니다.

예를 들어, 인스타그램 피드를 생각해보세요. 새 게시물이 올라오면 전체 페이지를 다시 로드하는 대신, 리액트는 새 게시물 부분만 업데이트합니다. 이렇게 하면 사용자는 페이지가 깜빡이는 것 없이 부드러운 경험을 할 수 있어요.

리액트의 핵심은 '컴포넌트'라는 개념입니다. 이것은 마치 레고 블록처럼 재사용 가능한 부품이에요. 버튼, 메뉴, 카드 등 웹사이트의 각 부분을 독립적인 컴포넌트로 만들고, 이 컴포넌트들을 조합해 전체 웹사이트를 구성합니다.

<br>

15. 버그를 해결한 경험

<br>

포트폴리오 프로젝트에서 방명록 기능 구현 중 CORS 정책 위반으로 API 요청이 차단되는 버그가 발생했습니다. 클라이언트와 서버가 서로 다른 도메인에서 호스팅되어 있어 발생한 문제였습니다. 이를 해결하기 위해 Nginx를 활용한 리버스 프록시를 구축하고, 동일 도메인에서 API를 호출하도록 설정했습니다. 또한 보안 강화를 위해 Certbot을 통해 SSL 인증서를 발급받아 HTTPS 프로토콜을 적용했습니다. 이 경험을 통해 웹 보안과 서버 인프라에 대한 실질적인 지식을 얻을 수 있었습니다.

<br>

16. 디자인시스템 프로젝트에 참여한다면 어떻게 시작할 것 같은지? 

<br>

디자인 시스템 프로젝트에 참여하게 된다면, 저는 먼저 기존 UI 요소들을 분석하여 패턴을 파악할 것입니다. 이후 디자이너와 개발자들과 협업하여 색상, 타이포그래피 같은 기본 디자인 토큰을 정의하고, 재사용 가능한 컴포넌트를 개발하겠습니다.

제가 이전 프로젝트에서 스타일컴포넌트를 활용해 스타일 코드의 재사용성을 높인 경험이 있어, 이를 디자인 시스템에도 적용할 수 있을 것 같습니다.

<br>

17. 성장을 위해서 노력하고 있는 지점?

<br>

현재 프론트엔드 개발 역량을 높이기 위해 React와 Next.js의 심화 개념을 꾸준히 학습하고 있습니다. 특히 공식 문서를 영어로 직접 읽으며 개념을 정확히 이해하려고 노력하고, 배운 내용을 실제 프로젝트에 적용해보는 과정을 반복하고 있습니다. 예를 들어, React의 useMemo와 useCallback 훅을 활용한 메모이제이션 최적화 기법을 실제 프로젝트에 적용해보고 있습니다. 또한 Next.js의 **동적 라우팅과 서버 컴포넌트**를 활용하여 **성능 최적화 및 사용자 경험 개선** 방법을 연구하고 있습니다.

<br>

18. 본사모토를 본인과 엮어 설명하자면?

<br>

팀스파르타의 "빠르게, 와우하게, 진정성있게"라는 모토는 제가 추구하는 개발 방식과 매우 일치합니다. "빠르게"는 제가 아마존 코리아 프로젝트에서 팀원 이탈 위기 상황을 신속하게 판단하고 대응했던 경험과 일치합니다. "와우하게"는 포트폴리오 웹사이트에서 멀티페이지 디자인, 연결리스트 구조의 방명록, 페이지 전환 애니메이션으로 차별화된 사용자 경험을 구현한 저의 접근 방식과 맞닿아 있습니다. "진정성있게"는 사용자 중심의 404 페이지와 커스텀 커서 구현을 통해 세심한 사용자 경험을 고려했던 저의 개발 태도를 반영합니다. 이러한 가치관을 바탕으로 팀스파르타에서 의미 있는 교육 서비스 개발에 기여하고 싶습니다.

<br>

19. 어떤 선임이 되고 싶은지?

<br>

기술적 역량과 함께 후배 개발자의 성장을 돕는 멘토가 되고 싶습니다. 제가 겪었던 문제와 해결 과정을 공유하고, 코드 리뷰를 통해 실질적인 피드백을 제공하는 선임이 되고자 합니다. 특히 팀스파르타의 교육 서비스를 개발하는 과정에서 얻은 지식과 경험을 체계적으로 정리하여 팀 내 지식 공유 문화를 만들어가고 싶습니다.

<br>

20. 본인이 생각했을때, 이전 직장에서 타인이 자신을 어덯게 생각했을 것 같은가?

<br>

아르바이트 경험을 돌이켜보면, 동료들은 저를 주어진 임무에 최선을 다하고 오히려 추가 업무까지 찾아서 하는 적극적인 사람으로 기억할 것 같습니다. 특히 한국은행이나 한화생명에서 직원들이 PC 장애로 도움을 요청할 때, 문제가 완전히 해결될 때까지 끈기 있게 매달리는 모습이 인상적이었을 것입니다. 한번은 윈도우 업데이트 후 네트워크 연결이 끊기는 문제가 발생했을 때, 퇴근 시간이 지났지만 드라이버 호환성 문제를 완전히 해결하고 나서야 귀가했던 경험이 있습니다.
